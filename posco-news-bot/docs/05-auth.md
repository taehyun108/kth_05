# 05 — 인증 · 접근 제어 · 배포

> INV-8: 인증은 서버에서. public/에 데이터를 두지 않는다.

### 3.2 배포·접근 아키텍처 (v1.4 — Vercel 전환)

> **v1.3까지의 구조:** public GitHub Pages(아카이브) + private repo(SWOT, 로컬에서만 열람).
> **v1.4:** Vercel 단일 앱 + **로그인 기반 3단 접근 레벨**. 저장소 이원화가 사라지고, SWOT을 모바일에서도 볼 수 있게 된다.

```
┌──────────────────────────────────────────────────────────────┐
│  PRIVATE REPO (단일)                                          │
│  ├─ app/            Next.js 앱                                │
│  ├─ data/           ★public/ 아님 — 서버에서만 읽는다★         │
│  │   ├─ articles.json      (L1)                              │
│  │   ├─ analysis.json      (L2) 시사점·swot_axis              │
│  │   ├─ issues.json        (L2) SWOT                          │
│  │   ├─ policies.json      (L1 보드 / L2 our_position)        │
│  │   └─ disputes.json      (L1 보드 / L2 affects_futurem)     │
│  ├─ pipeline/       수집·분석 (GitHub Actions에서 실행)        │
│  └─ cache/          원문 캐시 (.gitignore — 커밋 안 함)        │
└───────────────┬──────────────────────────────────────────────┘
                │ git push (Actions가 데이터 커밋)
                ▼
┌──────────────────────────────────────────────────────────────┐
│  VERCEL                                                       │
│  middleware.ts ── 세션 검증 ── 없으면 /login 리다이렉트        │
│                                                               │
│  /api/articles   → L1 인증 필요, articles.json 서빙            │
│  /api/policies   → L1                                         │
│  /api/disputes   → L1                                         │
│  /api/analysis   → ★L2 (allowlist)★                          │
│  /api/issues     → ★L2 (allowlist)★  SWOT                    │
│  /api/ask        → RAG 챗봇 (레벨에 따라 검색 범위 제한)       │
│                                                               │
│  /login  /posco  /policy  /trade  /swot(L2)                   │
└──────────────────────────────────────────────────────────────┘
```

#### 3.2.1 접근 레벨

| 레벨 | 대상 | 볼 수 있는 것 | 인증 |
|---|---|---|---|
| **L0** | 미인증 | `/login` 뿐. **데이터 일절 없음** | — |
| **L1** | 사내 구성원 | 기사 아카이브, 정책 보드, 통상 분쟁 보드, 클리핑, 챗봇(기사 한정) | 사내 도메인 이메일 |
| **L2** | 대외협력 담당자 | + **SWOT, 퓨처엠 시사점, `policy_ask`, `our_position`, `affects_futurem`**, 마스터 도구 | L1 + 이메일 **허용목록** |

> **v1.4로 무엇이 좋아졌나:** v1.3에서 SWOT은 "PC 앞에 앉아 로컬 서버를 띄워야" 볼 수 있었다. 이제 **출근길 휴대폰에서 열람**할 수 있다. 대외협력 업무 특성상 이 차이가 크다.

#### 3.2.2 ⚠️ 정적 사이트 때와 근본적으로 달라진 점

GitHub Pages에서는 `🔒마스터` 버튼이 **UI 토글에 불과**했다. `data/issues.json` URL만 알면 누구나 `curl`로 받을 수 있었다(§12.3 V3-1). Vercel에서는 **진짜로 막을 수 있다.** 단, 조건이 있다.

| 하면 안 되는 것 | 왜 |
|---|---|
| ❌ 데이터 JSON을 `public/` 에 두기 | `public/` 은 인증 없이 그대로 서빙된다. **Vercel로 옮겨도 유출 구조는 그대로다** |
| ❌ 클라이언트에서 `fetch('/data/issues.json')` | 위와 동일 |
| ❌ 전체 데이터를 내려준 뒤 프론트에서 필터링 | 네트워크 탭에 다 보인다 |
| ✅ `data/` 를 repo 루트에 두고 `/api/*`에서 `fs.readFile` | 서버에서만 읽힌다 |
| ✅ API가 **세션 레벨에 따라 필드를 걸러서** 응답 | L1 요청에는 `futurem_implication`을 아예 안 실어 보낸다 |

이것이 **INV-8**이다.

### 3.3 망분리 대응 — 3존 모델 (v1.5 신규)

#### 3.3.1 전제 재검토: 사내 도메인으로 옮길 필요가 있는가

§4.11.6에서 *"사내 계정 발신이 가장 안전"* 이라고 권장했으나, **그 권장은 v1.5에서 철회한다.**

| 근거 | 내용 |
|---|---|
| ① 수신 문제가 이미 해소됨 | 사내 배포 리스트 수신에 문제없음을 확인했다(P0-6 해소). 사내 발신으로 옮겨야 할 이유가 사라졌다 |
| ② **사내 발신은 파이프라인을 사내망에 가둔다** | 사내 SMTP를 쓰려면 발송 코드가 사내망에서 돌아야 한다. 그러면 같은 망에서 **뉴스 크롤링·카카오톡·Claude Code·Ollama 모델 다운로드가 전부 막힌다** |
| ③ 발신 주체와 실행 주체는 분리 가능 | 메일은 서버 간 통신이라 **사외 발신 → 사내 수신**이 망분리와 무관하게 성립한다 |

> **결론: 메일 발신은 사외 계정을 유지한다.** 옮기면 얻는 것(발신 도메인 일치)보다 잃는 것(파이프라인 전체)이 훨씬 크다.

#### 3.3.2 실제로 망분리가 걸리는 지점

문제는 **메일 발신이 아니라 웹 접속**이다.

| 존 | 기기 | 메일 수신 | 언론사 원문 | **Vercel 접속** | 카카오톡 | 파이프라인 실행 |
|---|---|---|---|---|---|---|
| **Z1 사내 업무망** | 회사 PC | ✅ | △ IT 정책 | **⚠️ 차단 가능** | ❌ | ❌ |
| **Z2 외부망** | 개인/외부망 PC | △ | ✅ | ✅ | ✅ | ✅ **여기서 실행** |
| **Z3 모바일** | 개인 휴대폰 | △ | ✅ | ✅ | ✅ | — |

**핵심 통찰 세 가지**

1. **카카오톡은 애초에 Z3(휴대폰)에서 쓴다.** 사내 PC에서 카톡을 쓸 일이 없다. **v2.1에서 Plan B로 전환되면서 발송이 서버에서 이뤄지므로 이 문제 자체가 사라졌다.** 팀원은 휴대폰으로 받기만 한다
2. **팀원이 카톡 링크를 눌러 Vercel에 들어가는 것도 Z3다.** 역시 무관하다
3. **진짜 제약은 Z1이다.** 회사 PC에서 메일을 읽다가 "전체보기" 링크를 눌렀을 때 Vercel이 막힐 수 있다

#### 3.3.3 INV-9 — 메일 자체 완결성

> **INV-9 (신규):** 메일은 **링크를 한 번도 누르지 않아도 업무가 되는 수준**으로 자체 완결적이어야 한다. Z1(사내 PC)에서 Vercel이 막혀도 메일만으로 "어느 매체가 무엇을 어떻게 썼는지"와 "어떤 정책·통상 조치가 어느 단계인지"를 파악할 수 있어야 한다.

| 항목 | 조치 |
|---|---|
| 요약 분량 | 카드용 1~2문장이 아니라 **본문에 `bullets`까지 전개**한다 |
| 링크 우선순위 | **① 언론사 원문 URL**(Z1에서도 대체로 열림) → ② Vercel 상세 |
| Vercel 링크 표기 | `전체보기(로그인)` 로 명시해 Z1에서 헛클릭을 줄인다 |
| 보드 정보 | 정책·분쟁 **단계 배지를 메일 본문에 텍스트로** 넣는다. 보드를 보러 들어가지 않아도 되게 |
| 이미지 | 여전히 없음 — 사내 메일 게이트웨이가 외부 이미지를 차단하는 경우가 많다 |

> 이 원칙이 지켜지면 **Vercel 접속 가능 여부가 리스크에서 편의 문제로 격하된다.** 막히면 불편할 뿐 업무가 멈추지 않는다.

#### 3.3.4 실행 위치 정리

```
Z2 외부망 PC  ← 셀프호스트 러너 겸용
 ├─ 파이프라인 L1(Ollama) · L2(Claude Code)
 ├─ 사외 메일 계정으로 SMTP 발송
 └─ git push → Vercel 배포

Z3 모바일
 ├─ 카톡 발송 패널 (복사 → 붙여넣기)
 └─ Vercel 열람 (SWOT 포함, L2 세션)

Z1 사내 PC
 └─ 메일 수신 · 열람 (자체 완결 · INV-9)
```

> 별도 외부망 회선을 두신다면 **그 PC가 곧 셀프호스트 러너**다. 이미 v1.1에서 "L1·L2는 로컬 PC에서 실행"으로 설계돼 있으므로 **구조 변경 없이 그대로 들어맞는다.**

### F-12. 인증 및 접근 제어 (v1.4 신규)

#### 4.12.1 Vercel 내장 Deployment Protection을 쓰지 않는 이유

먼저 검토했으나 **요건에 맞지 않는다.**

| 방식 | 문제 |
|---|---|
| **Vercel Authentication** (무료·전 플랜) | <cite index="16-1">이미 Vercel 팀에 로그인한 사람만 통과시킨다.</cite> 팀원 전원이 Vercel 계정을 만들고 팀 시트를 차지해야 한다 (Pro 기준 시트당 과금) |
| **Password Protection** | <cite index="12-1">Enterprise 플랜이거나 Pro에 월 $150 Advanced Deployment Protection 애드온이 필요하다.</cite> 연 $1,800 |
| **Standard Protection 범위** | <cite index="12-1">프리뷰와 생성된 배포 URL만 덮고 커스텀 프로덕션 도메인은 공개로 남는다.</cite> Hobby에서는 프로덕션 도메인을 아예 잠글 수 없다 |
| **Trusted IPs** | 사내망 IP만 허용 → 재택·모바일 불가. 상위 플랜 기능 |

**결정적 한계:** Deployment Protection은 **전부 아니면 전무**다. 우리는 L1(기사)과 L2(SWOT)를 **같은 사이트 안에서 다르게** 취급해야 한다. 배포 단위 보호로는 이게 불가능하다.

→ **앱 레벨 인증(Next.js middleware + 세션)** 을 직접 구현한다. 무료이고, 역할 분리가 되고, 감사 로그도 남는다.

#### 4.12.2 인증 방식 — 로그인 코드 (v1.5 변경)

| 방식 | 사내 협조 | 개인 식별 | 망분리 대응 | 판정 |
|---|---|---|---|---|
| ~~매직링크 (일회용 링크)~~ | 불필요 | ✅ | **❌ 기기를 건너뛴다** | v1.5에서 탈락 |
| **로그인 코드 (6자리 숫자)** | 불필요 | ✅ | ✅ | ✅ **채택** |
| SSO (Entra ID / Workspace OAuth) | **앱 등록 필요** | ✅ | ✅ | 사내 승인 나면 v2 전환 |
| 공유 비밀번호 + 서명 쿠키 | 불필요 | ❌ | ✅ | L2 부적합 (누가 SWOT을 봤는지 모름) |
| Vercel Authentication | 팀 시트 필요 | ✅ | ✅ | ❌ (§4.12.1) |

> ⚠️ **왜 매직링크가 탈락했는가 (망분리 때문):**
> 매직링크는 **메일을 여는 기기와 접속하는 기기가 같아야** 성립한다. 그런데 우리 상황은 정반대다.
> **메일은 Z1(사내 PC)에서 읽고, Vercel 접속은 Z3(모바일)에서 한다.**
> 사내 PC에서 링크를 눌러도 Vercel이 막혀 인증이 실패하고, URL을 휴대폰으로 옮겨 적는 것은 현실적이지 않다.
> **로그인 코드는 이 문제가 없다.** 사내 PC 메일에서 숫자 6자리를 보고 휴대폰에 입력하면 끝이다.

```
① 휴대폰 브라우저 /login 에서 사내 이메일 입력
② 도메인 화이트리스트 검증  ← 아니면 즉시 거절
③ 6자리 코드를 사내 메일로 발송 (10분 만료)
④ 사내 PC 메일함에서 코드 확인 → 휴대폰에 입력
⑤ 세션 쿠키 발급 (httpOnly, Secure, SameSite=Lax, 30일)
⑥ 이메일이 L2 허용목록에 있으면 role=admin
```

**코드 방식의 보안 보강 (숫자 6자리는 무차별 대입에 약하다)**

| 항목 | 값 |
|---|---|
| 만료 | 10분 |
| 시도 횟수 | **5회 실패 시 코드 폐기** + 재발급 필요 |
| 발급 제한 | 이메일당 5분 내 3회 |
| 일회성 | 성공 시 즉시 폐기, 재사용 불가 |
| 세션 고정 방지 | 코드 발급 시 브라우저에 논스를 심고 검증 시 대조 — **다른 기기에서 가로챈 코드로는 로그인 불가** |

**세션 정책**

| 항목 | 값 | 근거 |
|---|---|---|
| 유효기간 | **30일** | 카톡·메일 링크를 누를 때마다 로그인하면 아무도 안 쓴다 |
| 갱신 | 접속 시 슬라이딩 연장 | |
| L2 재확인 | `/swot/` 최초 진입 시 **재인증 없음**, 단 접근 로그 기록 | 마찰을 늘리면 안 쓰게 된다. 대신 감사로 통제 |
| 강제 만료 | 허용목록에서 제거 시 즉시 세션 무효 | 인사이동 대응 |

#### 4.12.3 링크 진입 UX

카톡·메일의 링크를 눌렀을 때 로그인 벽이 뜨는 흐름이 매끄러워야 한다.

```
[Z3 모바일] 카톡 링크 클릭
  → 세션 있음(30일) → 해당 기사로 바로 이동          ← 평상시 대부분
  → 세션 없음 → /login?next=/posco/articles/<id>
                코드 입력 후 ★원래 보려던 기사로 복귀★

[Z1 사내 PC] 메일의 `전체보기(로그인)` 클릭
  → Vercel 접속 가능 → 정상 동작
  → 차단 → ★메일 본문만으로 이미 업무가 된다 (INV-9)★
```

- `next` 파라미터는 **자체 경로만** 허용한다 (오픈 리다이렉트 방지)
- 카톡 메시지의 **OG 카드는 언론사 원문 링크**라 로그인과 무관하다. 로그인이 걸리는 건 `전체보기`뿐이고, 세션이 30일이라 실제로는 **한 달에 한 번 코드를 입력**하는 수준이다
- 메일 링크에는 `(로그인)` 표기를 붙여 Z1에서의 헛클릭을 줄인다

#### 4.12.4 API 응답 필드 필터링

```ts
// app/api/articles/route.ts
const L2_ONLY = ['futurem_implication','swot_axis','sector_impact',
                 'frame','tone_evidence','policy_ask_hint','fact_check_flags','body'];

export async function GET(req: Request) {
  const s = await getSession(req);
  if (!s) return new Response('Unauthorized', { status: 401 });

  const raw = JSON.parse(await fs.readFile('data/articles.json','utf8'));
  const articles = s.role === 'admin'
    ? withAnalysis(raw)                       // analysis.json 병합
    : raw.articles.map(a => omit(a, L2_ONLY)); // ★L1은 아예 안 내려보낸다★
  return Response.json({ ...raw, articles });
}
```

> **핵심:** L1에게는 L2 필드를 **응답에 담지 않는다.** 담아놓고 화면에서 숨기면 네트워크 탭에 그대로 보인다. INV-8의 실체가 이 코드다.

#### 4.12.5 감사 로그

| 기록 대상 | 항목 |
|---|---|
| 로그인 | 이메일, 시각, IP, User-Agent |
| **`/api/issues` 접근 (SWOT)** | 이메일, 시각, 조회 이슈 id |
| `/api/analysis` 접근 | 동일 |
| 허용목록 변경 | 변경자, 대상, 시각 |
