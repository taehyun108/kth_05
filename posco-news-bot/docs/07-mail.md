# 07 — 일일 브리핑 메일

> INV-7: 메일도 SWOT 차단 대상.
> INV-9: 메일은 자체 완결적 — 링크 없이도 업무가 된다.

### F-11. 일일 브리핑 메일 (v1.3 개정 — 2부 구성)

> **요구사항 (v1.3 갱신):**
> ① 전날 포스코 관련 기사를 **어느 업체에서 어떤 내용으로 보도했는지** 정리해 발송 → **Part A**
> ② T3·T4(정책·통상) 중 포스코 미언급분은 카톡 대신 **메일로만** 전달 → **Part B**
> ③ 발송 시각 **07:00**
> ④ 사외 계정에서 **사내 단체 메일(배포 리스트)** 로 발송

#### 4.11.1 이 기능의 성격

카톡·텔레그램 브리핑과 목적이 다르다. 브리핑은 *"무슨 일이 있었나"* 이고, 클리핑 메일은 **"어느 매체가 우리를 어떻게 다뤘나"** 다. 대외협력 관점에서는 후자가 더 중요할 때가 많다. 같은 사안을 A매체는 우호적으로, B매체는 비판적으로 쓴다면 그 차이 자체가 대응 정보다.

→ 따라서 **정렬 기준이 시간이 아니라 언론사**다.

**Part A / Part B 구분 기준**

| | Part A | Part B |
|---|---|---|
| 대상 | `posco_relevance ∈ {primary, mention}` | `track ∈ {policy, trade}` **AND** `posco_relevance = none` **AND** `impact ≥ mid` |
| 정렬 | **언론사별** | **트랙·카테고리별** |
| 관심사 | "누가 우리를 어떻게 썼나" | "무슨 제도·조치가 어느 단계인가" |
| 표시 | 논조 배지, 매체별 대비 | 국가 플래그, 단계 배지, 품목 해당 여부 |
| 카톡 중복 | 있음 (같은 기사가 카톡에도) | **없음 — 메일에서만 볼 수 있는 내용** |

> Part B는 **카톡에 안 가는 내용**이므로, 메일을 안 읽으면 아예 못 본다. 그래서 제목에 건수를 노출한다: `[포스코 브리핑] 8/26(수) 포스코 12건 · 정책통상 8건`

- **④ 대비 섹션**은 같은 `issue_id`에 2개 이상 매체가 붙었을 때만 생성한다
- 요약은 **자체 작성 문장 + 원문 링크**만 싣는다. 기사 본문 전재 금지 (§9.2)
- **SWOT·`policy_ask`·`futurem_implication`·`frame`은 싣지 않는다 (INV-7)**

#### 4.11.3 대상 범위 (결정 필요 항목 있음)

| 항목 | 기본값 | 비고 |
|---|---|---|
| 대상 기사 | Part A: `posco_relevance ≠ none` / Part B: 정책·통상 미언급분 | Part A는 카톡과 동일 기준 |
| 기간 | 전일 00:00~24:00 | 카톡 브리핑(07:00 기준 24시간)과 경계가 다름 → §13 P1-8 |
| 발송 시각 | **07:00** | 야간 배치로 전일분을 미리 완성해 두고 **발송만** 수행 (§6.4) |
| 수신자 | `MAIL_TO_GROUP` — **사내 배포 리스트 주소 1개** | §F-11.6 참조 |
| 포맷 | HTML + 텍스트 폴백 | 사내 메일 클라이언트 호환 |

#### 4.11.4 품질 폴백 (논조 미확정 시)

논조(`tone`)는 L1·L2 산출물이다. PC가 꺼져 있어 야간 배치가 L0에서 멈추면 논조 칸이 비어 있다.

```
06:40  L1·L2 완료 여부 확인
  ├─ 완료   → 논조·매체별 대비 포함 전체 포맷으로 발송
  └─ 미완료 → 셀프호스트 재시도 1회 (10분)
       ├─ 성공 → 전체 포맷
       └─ 실패 → ★논조 열·Part A ④(매체별 대비) 제외★
                  "언론사별 보도 목록" 형태로 07:00 정시 발송
```

**메일을 거르지 않는다 (INV-6).** 논조 없는 목록만으로도 "어느 매체가 몇 건 썼는지"는 전달되고, 그게 이 메일의 최소 가치다. 이 경우 제목에 `(요약본)`을 붙여 구분한다.

#### 4.11.5 발송 구현 (API 키 불요)

```python
SMTP_HOST = "smtp.gmail.com"; SMTP_PORT = 587   # 개인/사외 Gmail + 앱 비밀번호
# 사내 릴레이 사용 가능 시 사내 SMTP 주소로 교체 (권장)
```

- 발송은 **클라우드 러너에서도 가능**하다 (SMTP는 로컬 PC 불필요)
- 발송 성공/실패를 `dispatch_log`에 기록. 실패 시 텔레그램 `#운영-알림` 통지
- **Bounce 수신 처리**: 배포 리스트가 반송되면 조용히 실패한다. 반송 메일함을 주 1회 확인하거나, 발신 계정 자신을 `Bcc`에 넣어 **도달 여부를 자가 확인**한다

#### 4.11.6 사외 → 사내 단체 메일 발송 검토 (v1.3 신규)

**질문:** 수신자 10명 이하가 아니라 **단체 메일(배포 리스트)로 묶으면 가능한가?**
**답:** **발송 한도 문제는 완전히 해결된다.** 다만 병목이 다른 곳으로 옮겨간다.

**① 발송 한도 — 해결됨 ✅**

배포 리스트 주소 1개로 보내면 **발신자 입장에서 수신자는 1명**이다. 팬아웃은 수신 측 그룹 서버가 처리한다.

| 항목 | 수치 | 우리 사용량 |
|---|---|---|
| 개인 Gmail 일일 발송 | 500통 (24시간 롤링) | **1통/일** |
| Google Workspace 일일 발송 | 2,000통 | 동일 |
| **SMTP 경유 메시지당 수신자** | **100명** ← 실질 제약 | **1명 (그룹 주소)** |

> Gmail 공식 문서도 한도 초과를 피하는 방법으로 **"모든 수신자를 포함한 그룹을 만들어 그룹 주소로 전송"** 을 안내한다. 우리 방식이 정확히 그것이다.
> ⚠️ **`Bcc`에 수십 명을 넣는 방식은 쓰지 말 것.** 수신자 수가 그대로 카운트되고 스팸 점수도 올라간다. 배포 리스트가 모든 면에서 낫다.

**② 진짜 병목 — 사내 수신 정책 ⚠️**

발송이 아니라 **수신 쪽에서 막힌다.** 대부분의 조직은 사내 배포 리스트를 내부 전용으로 잠가 둔다.

| 관문 | 확인 사항 | 막히면 |
|---|---|---|
| **배포 리스트 외부 수신 허용** | 그룹 주소가 외부 발신자 메일을 받도록 설정돼 있는가 | 발신자 주소를 그룹 허용 목록에 등록 요청 |
| **메일 보안 게이트웨이** | 외부에서 오는 자동화·정기 메일을 격리하는가 | 발신 주소 화이트리스트 등록 요청 |
| **SPF / DKIM / DMARC** | Gmail 발신은 gmail.com 도메인으로 인증되므로 통과 가능 | 자체 도메인 사용 시 DNS 설정 필요 |
| **사내 정보보호 정책** | 외부 계정에서 사내 다수에게 정기 발송이 허용되는가 | 사내 계정 발신으로 전환 |

**③ 권장 순서**

| 순위 | 방식 | 장단 |
|---|---|---|
| **1** | **사내 계정에서 발신** (사내 SMTP 릴레이 / Exchange) | 사내→사내라 필터 통과가 가장 쉽다. **가능하면 이걸로** |
| 2 | 사외 Gmail 발신 + 배포 리스트 + **화이트리스트 등록** | IT 협조 1회면 안정적 |
| 3 | 사외 Gmail 발신 + 배포 리스트 (등록 없이) | 초기엔 되다가 스팸 학습으로 막힐 수 있음 |
| 4 | 사외 Gmail + 개별 수신자 20명 이하 | 관리 부담, 인원 변동 시 수정 필요 |
| 5 | 메일 포기 → **텔레그램 `#브리핑` 채널** | 포맷만 바꾸면 되므로 구현 비용 거의 0 |

**④ 도달률을 위한 기술 조치**

| 항목 | 조치 |
|---|---|
| 제목 접두어 고정 | `[포스코 브리핑]` — 사내 규칙 필터로 폴더 자동 분류 유도 |
| `List-Id` 헤더 | `List-Id: posco-news.internal` — 자동 발송임을 명시해 필터가 뉴스레터로 분류하게 |
| `List-Unsubscribe` 헤더 | 수신 거부 경로 제공 (스팸 점수 하락) |
| 발신 전용 계정 분리 | 개인 업무 메일과 섞지 않는다. 한쪽이 막혀도 다른 쪽 영향 없음 |
| multipart | HTML + 텍스트 폴백 동시 제공 |
| 링크 | 단축 URL 금지, 도메인 최소화, 링크 대비 텍스트 비중 유지 |
| 이미지·첨부 | **없음** — 썸네일 이미지도 넣지 않는다. 첨부는 스팸 점수와 사내 검역에 가장 취약 |
| 발송 리듬 | 매일 같은 시각 1통. 갑작스러운 다중 발송 금지 |

**⑤ 초기 검증 절차**

```
1주차: 본인 사내 주소로만 발송 → 스팸함 여부 확인
2주차: 팀원 2~3명 추가 → 도달 확인
3주차: 배포 리스트 전환 → 반송·격리 확인
   ↳ 이 단계에서 막히면 IT에 화이트리스트 등록 요청
```

> 처음부터 배포 리스트로 쏘면 **한 번의 스팸 신고로 발신 계정이 통째로 차단**될 수 있다. 단계적으로 올린다.

### F-13. 주간 브리프 (v2.0 신규 — 요구사항 E5·E6)

> **요구사항:** *"월요일에 주간 기사 내용 요약 및 향후 대응 방안 예측"*

**실행:** 월요일 07:30 (셀프호스트 · L2) → 메일 + 웹 `/weekly/`

#### 4.13.1 구성

```
[주간 브리프] 2026-W35 (8/19~8/25)

① 한 주 요약
   총 214건 · 포스코 68 · 산업 92 · 정책 34 · 통상 20
   논조: 긍정 41 / 중립 132 / 부정 39 / 위기 2
   전주 대비: 부정 +12건 ▲   ← 추세가 핵심

② 이번 주 핵심 이슈 (3~5개)
   각 이슈: 기사 수 · 논조 분포 · 퓨처엠 기준 SWOT 요약 · 대응 상태

③ 매체 동향
   우리를 가장 많이 다룬 매체 / 논조가 부정으로 기운 매체
   → 프레임 변화 감지

④ 법령·정책 캘린더 ★
   · 의견제출 마감 임박: 이차전지 특별법 시행령 (D-9)
   · 시행 예정: 화관법 개정 시행 (10/1)
   · 예고 신규: 2건

⑤ 향후 전망 (outlook) ★요구사항 E6★
```

#### 4.13.2 `outlook` — 향후 대응 방안 예측

> ⚠️ **예측은 할루시네이션이 가장 잘 나오는 영역이다.** "예측"을 자유롭게 시키면 그럴듯한 창작이 나온다. 그래서 **근거가 있는 것만, 신뢰도를 붙여서** 생성한다.

```yaml
outlook:
  scheduled:                    # ★확정된 일정 — 예측이 아니라 사실★
    - date: "2026-09-29"
      event: "이차전지 특별법 시행령 의견제출 마감"
      action: "제12조 음극재 포함 의견서 제출"
      confidence: certain
  likely:                       # 근거 있는 전개
    - text: "45X 개정안 의견수렴이 10월 종료되면 연내 최종규칙 공표 가능성"
      basis: ["2026-08-26-a3f9c1d2e8"]     # ★근거 기사 필수★
      confidence: medium
      watch: "Federal Register 최종규칙 공고"
  monitoring:                   # 근거는 약하나 주시 필요
    - text: "중국 흑연 수출통제 품목 추가 여부"
      basis: []
      confidence: low
  recommended_actions:          # 대응방안 초안 (요구사항 C7)
    - "① 9월 2주까지 제12조 의견서 초안 완료"
    - "② 북미 원가 데이터 체계 점검 착수"
```

**생성 규칙 (프롬프트에 명시)**

| 규칙 | 이유 |
|---|---|
| `scheduled`는 **날짜가 확정된 것만** | 여기에 추측이 섞이면 캘린더 전체를 못 믿는다 |
| `likely`는 **근거 기사 id 필수**, 없으면 `monitoring`으로 강등 | 근거 없는 예측 차단 |
| 수치 예측 금지 (가격·점유율·실적) | 검증 불가하고 틀리면 신뢰도가 무너진다 |
| `recommended_actions`는 **우리가 실제로 할 수 있는 행동**만 | "시장을 주시한다" 같은 문장 금지 |
| 전부 **L2 전용** | 대응방안은 내부 판단 (INV-3) |

> 메일에는 `scheduled`(사실)와 `recommended_actions` 중 **비민감 항목만** 싣고, `likely`·`monitoring`은 웹 `/weekly/`(L2)에서 본다.
