## 0.1 착수 요약 (Executive Summary)

> 이 문서는 **13회 검증**을 거친 확정본이다. 처음 여는 사람은 이 절 → §0.5 추적표 → §15 퀵스타트 → §10 로드맵 순으로 보면 된다.

### 무엇을 만드는가

포스코 그룹·이차전지 산업·정책·법령·통상 뉴스를 **자동 수집 → 요약 → 포스코퓨처엠 기준 영향도·SWOT 분석 → 다채널 배포**하는 시스템. 사람은 **질문만** 한다.

### 4개 트랙

| | 대상 | 웹 탭 | 카톡 | 메일 |
|---|---|---|---|---|
| **T1 포스코** | 그룹 7개 계열사 | `/posco/` | ✅ | Part A |
| **T2 이차전지 산업** | 국내외 셀·소재·원료사 | `/posco/` | 포스코 언급 시 | Part A/B |
| **T3 정책·법령** | 지원제도·행정예고·시장전망 | `/policy/` | 포스코 언급 시 | Part B |
| **T4 통상·규제** | 관세·수출통제·무역구제 | `/trade/` | 포스코 언급 시 | Part B |

### 핵심 설계 결정 8가지

| # | 결정 | 이유 |
|---|---|---|
| 1 | **카톡 발송 기준은 트랙이 아니라 `posco_relevance`** | 통상 기사여도 포스코퓨처엠이 언급되면 보낸다 (§1.3) |
| 2 | **SWOT 기준점은 항상 포스코퓨처엠** | 경쟁사·정책 기사도 "우리에게 무엇인가"로 해석 (INV-2) |
| 3 | **SWOT은 웹에서만** — 카톡·메일·텔레그램에 절대 미포함 | 발송 코드가 SWOT 파일을 import조차 하지 않음 (INV-3) |
| 4 | **LLM은 소량·고가치에만** — 대량 요약은 규칙+로컬 | Groq 무료 티어로는 물량 미달. API 키 없이 $0 구성 (§11.6) |
| 5 | **07:00은 만드는 시각이 아니라 보내는 시각** | 전일 기사는 자정에 확정 → 야간 배치 (§6.4) |
| 6 | **인증은 서버에서** — 데이터는 `/api/` 뒤 | 정적 사이트의 가짜 잠금 문제 해소 (INV-8) |
| 7 | **`crisis` 논조는 자동 발송 금지** | 홍보실 방침이 먼저 정해져야 하는 사안 (§4.7.5) |
| 8 | **카톡 출력 포맷 🔒고정** — 링크 카드 + `[매체명]` 요약 2메시지 | 형태가 깨질 바에는 미발송. 코드로 강제 (INV-10, §4.7.3) |

```

```

## 1. 프로젝트 개요

### 1.1 목적

포스코 그룹사 · 국내외 이차전지 산업 · **국내외 정책/규제/시장 트렌드** 3개 영역의 뉴스를
자동 수집 → 본문 크롤링 → 요약 → **포스코퓨처엠 관점의 SWOT/대응방안 도출** → 채널별 차등 배포한다.

대외협력 업무 관점의 세 가지 질문에 매일 아침 5분 안에 답하는 것이 목표다.

1. **"우리 그룹에 대해 언론이 무슨 말을 하고 있는가"** → T1 포스코 트랙
2. **"경쟁사·전방산업이 어떻게 움직이고, 그게 퓨처엠에 무슨 의미인가"** → T2 산업 트랙
3. **"국내외 정책·규제가 어디로 가고 있고, 우리가 정부에 무엇을 건의해야 하는가"** → T3 정책 트랙

### 1.2 배경

- 그룹사 뉴스 모니터링이 수기 검색 + 수기 요약 + 수기 카톡 공유로 진행 → 반복 노동
- 기사 건수는 많은데 **"이게 우리에게 위협인가 기회인가"** 판단은 사람 머릿속에만 있음
- 경쟁사(에코프로·엘앤에프·CATL) 뉴스는 그 자체로는 우리 뉴스가 아니지만 **SWOT의 T·O 원천**
- **정책 트랙은 대외협력 업무의 직접 산출물과 연결된다.** 해외 지원정책 벤치마킹 → 정부 협의 자료 → 부처 제출 자료로 이어지는 흐름을, 매일 자동 축적되는 아카이브가 뒷받침한다
- 기존 `KTH_01/news` 아카이브에서 **카드형 정적 아카이브 + GitHub Actions 파이프라인** 패턴이 검증됨
- 기존 `KTH_01/trade` (나라별 통상정책 현황) 페이지와 T3가 주제적으로 겹침 → §4.5.6에서 통합 방안 정의

> ⚠️ **"T3·T4 카톡 제외"의 정확한 의미 (v1.3 해석 확정)**
> 판별 기준은 **트랙이 아니라 `posco_relevance`** 다. 실제 사례로 확인된다.
>
> > *「미·캐나다 '관세전쟁' 불똥?…산업계 '촉각'」 (뉴스토마토)* → `track: trade`(T4)이지만 본문에 **"포스코퓨처엠은 퀘백주에 GM과 함께 양극재 합작사 얼티엄캠을 설립하고 연산 3만톤 규모의 생산기지를 짓고 있습니다"** 가 들어 있다 → `posco_relevance: mention` → **카톡 발송 대상**
>
> 즉 T3·T4에서 카톡으로 안 가는 것은 **포스코가 한 번도 언급되지 않은 순수 정책·통상 기사**다. 이건 메일 Part B로만 간다.
> 이 해석은 §13.0 P0-2 철회와도 일관된다 — 포스코 미언급 정책 기사를 억지로 카톡에 넣던 "정책 알림 블록"이 없어진 것이지, 포스코가 나오는 통상 기사를 빼는 게 아니다.

#### T2 / T3 경계 판정 규칙 (모호성 제거)

기사 1건이 T2인지 T3인지 헷갈리는 경우가 실제로 매우 많다. 아래 순서로 판정한다.

```
1. 기사의 주된 행위 주체가 "정부·규제기관·국제기구·조사기관"인가?  → T3
2. 기사의 주된 행위 주체가 "특정 기업"인가?                        → T2
3. 둘 다인 경우 (예: "정부, 포스코퓨처엠 등에 세액공제 확대")
   → 제목의 주어를 따른다. 제목 주어가 정부면 T3.
4. 시장 통계·전망·점유율 리포트 (SNE리서치, IEA, BNEF)             → T3 (pol-trend)
5. 기업의 정책 대응/건의 활동 (예: "배터리협회, 정부에 건의")        → T3
6. 판정 불가 시 → T2로 두고 `track_ambiguous: true` 플래그
```

> 판정 결과는 `track` 1개만 갖되, `also_tracks[]`에 부차 트랙을 기록해 필터에서 양쪽 모두 노출되게 한다. (예: "정부, 포스코퓨처엠 세액공제 확대" → `track: policy`, `also_tracks: ["posco"]`)

#### 3.2.2 ⚠️ 정적 사이트 때와 근본적으로 달라진 점

GitHub Pages에서는 `🔒마스터` 버튼이 **UI 토글에 불과**했다. `data/issues.json` URL만 알면 누구나 `curl`로 받을 수 있었다(§12.3 V3-1). Vercel에서는 **진짜로 막을 수 있다.** 단, 조건이 있다.

| 하면 안 되는 것 | 왜 |
|---|---|
| ❌ 데이터 JSON을 `public/` 에 두기 | `public/` 은 인증 없이 그대로 서빙된다. **Vercel로 옮겨도 유출 구조는 그대로다** |
| ❌ 클라이언트에서 `fetch('/data/issues.json')` | 위와 동일 |
| ❌ 전체 데이터를 내려준 뒤 프론트에서 필터링 | 네트워크 탭에 다 보인다 |
| ✅ `data/` 를 repo 루트에 두고 `/api/*`에서 `fs.readFile` | 서버에서만 읽힌다 |
| ✅ API가 **세션 레벨에 따라 필드를 걸러서** 응답 | L1 요청에는 `futurem_implication`을 아예 안 실어 보낸다 |

이것이 **INV-8**이다.


### 3.3 망분리 대응 — 3존 모델 (v1.5 신규)

#### 3.3.1 전제 재검토: 사내 도메인으로 옮길 필요가 있는가

§4.11.6에서 *"사내 계정 발신이 가장 안전"* 이라고 권장했으나, **그 권장은 v1.5에서 철회한다.**

| 근거 | 내용 |
|---|---|
| ① 수신 문제가 이미 해소됨 | 사내 배포 리스트 수신에 문제없음을 확인했다(P0-6 해소). 사내 발신으로 옮겨야 할 이유가 사라졌다 |
| ② **사내 발신은 파이프라인을 사내망에 가둔다** | 사내 SMTP를 쓰려면 발송 코드가 사내망에서 돌아야 한다. 그러면 같은 망에서 **뉴스 크롤링·카카오톡·Claude Code·Ollama 모델 다운로드가 전부 막힌다** |
| ③ 발신 주체와 실행 주체는 분리 가능 | 메일은 서버 간 통신이라 **사외 발신 → 사내 수신**이 망분리와 무관하게 성립한다 |

> **결론: 메일 발신은 사외 계정을 유지한다.** 옮기면 얻는 것(발신 도메인 일치)보다 잃는 것(파이프라인 전체)이 훨씬 크다.

#### 3.3.2 실제로 망분리가 걸리는 지점

문제는 **메일 발신이 아니라 웹 접속**이다.

| 존 | 기기 | 메일 수신 | 언론사 원문 | **Vercel 접속** | 카카오톡 | 파이프라인 실행 |
|---|---|---|---|---|---|---|
| **Z1 사내 업무망** | 회사 PC | ✅ | △ IT 정책 | **⚠️ 차단 가능** | ❌ | ❌ |
| **Z2 외부망** | 개인/외부망 PC | △ | ✅ | ✅ | ✅ | ✅ **여기서 실행** |
| **Z3 모바일** | 개인 휴대폰 | △ | ✅ | ✅ | ✅ | — |

**핵심 통찰 세 가지**

1. **카카오톡은 애초에 Z3(휴대폰)에서 쓴다.** 사내 PC에서 카톡을 쓸 일이 없다. **v2.1에서 Plan B로 전환되면서 발송이 서버에서 이뤄지므로 이 문제 자체가 사라졌다.** 팀원은 휴대폰으로 받기만 한다
2. **팀원이 카톡 링크를 눌러 Vercel에 들어가는 것도 Z3다.** 역시 무관하다
3. **진짜 제약은 Z1이다.** 회사 PC에서 메일을 읽다가 "전체보기" 링크를 눌렀을 때 Vercel이 막힐 수 있다

#### 3.3.3 INV-9 — 메일 자체 완결성

> **INV-9 (신규):** 메일은 **링크를 한 번도 누르지 않아도 업무가 되는 수준**으로 자체 완결적이어야 한다. Z1(사내 PC)에서 Vercel이 막혀도 메일만으로 "어느 매체가 무엇을 어떻게 썼는지"와 "어떤 정책·통상 조치가 어느 단계인지"를 파악할 수 있어야 한다.

| 항목 | 조치 |
|---|---|
| 요약 분량 | 카드용 1~2문장이 아니라 **본문에 `bullets`까지 전개**한다 |
| 링크 우선순위 | **① 언론사 원문 URL**(Z1에서도 대체로 열림) → ② Vercel 상세 |
| Vercel 링크 표기 | `전체보기(로그인)` 로 명시해 Z1에서 헛클릭을 줄인다 |
| 보드 정보 | 정책·분쟁 **단계 배지를 메일 본문에 텍스트로** 넣는다. 보드를 보러 들어가지 않아도 되게 |
| 이미지 | 여전히 없음 — 사내 메일 게이트웨이가 외부 이미지를 차단하는 경우가 많다 |

> 이 원칙이 지켜지면 **Vercel 접속 가능 여부가 리스크에서 편의 문제로 격하된다.** 막히면 불편할 뿐 업무가 멈추지 않는다.

#### 3.3.4 실행 위치 정리

```
Z2 외부망 PC  ← 셀프호스트 러너 겸용

 ├─ 카톡 발송 패널 (복사 → 붙여넣기)
```

#### 4.1.3-A 법령 트랙 (`pol-law`) 상세 — v2.0 신규

> **요구사항 C4:** *"[법령] 행정예고 시 당사 영향 및 SWOT 분석"*
> 법령은 뉴스와 성격이 다르다. **기사가 나기 전에 관보·예고 단계에서 잡아야** 대응 시간이 생긴다. 시행된 뒤 기사로 아는 것은 이미 늦다.

**수집 소스 (뉴스보다 원문이 우선)**

| 소스 | 방식 | 잡히는 것 | 안정성 |
|---|---|---|---|
| **국가법령정보센터 Open API** (법제처) | 무료 API (인증키 신청 필요) | 법령 제·개정, 시행일, 조문 | 높음 |
| **입법예고** (국회·정부) | 목록 페이지 | 법률안 예고 | 중간 |
| **행정예고** (부처 공고) | 관보·부처 게시판 | 고시·훈령·예규 개정 | 중간 |
| 대한민국 전자관보 | 공고 | 공포 확정 | 높음 |
| 규제정보포털 | 규제영향분석서 | **규제 신설 시 산업 영향 분석 원문** | 중간 |
| 뉴스 | 기존 파이프라인 | 해설·업계 반응 | — |

> ⚠️ 국가법령정보센터 API는 **무료지만 인증키 신청이 필요**하다. §11.6의 "API 키 불요" 원칙은 **LLM에 한한 것**이며, 공공데이터 API는 예외로 둔다. 신청이 지연되면 목록 페이지 파싱으로 대체한다.

**법령 엔티티 (`private/data/laws.json`)**

정책·분쟁과 동일하게 **법령 자체를 엔티티로 관리**하고, 예고·공포·시행을 상태 변화로 기록한다.

```jsonc
{
  "laws": [
    {
      "law_id": "kr-battery-special-act",
      "name": "이차전지산업 경쟁력 강화 및 지원에 관한 특별법",
      "ministry": "산업통상자원부",
      "type": "법률",                      // 법률 | 시행령 | 시행규칙 | 고시 | 훈령
      "current_stage": "notice",           // draft|notice(예고)|passed|promulgated|effective|amended
      "notice_period": { "from": "2026-08-20", "to": "2026-09-29" },
      "effective_date": null,
      "affects_futurem": true,
      "affected_articles": ["제12조 세제지원", "제18조 인력양성"],
      "obligation_type": ["지원", "신고의무"],   // 지원 | 규제 | 신고의무 | 처벌
      "timeline": [
        { "date": "2026-08-20", "stage": "notice", "source": "행정예고 제2026-000호",
          "article_ids": ["..."], "note": "40일 예고" }
      ],
      "our_position": "제12조 적용대상에 음극재 포함 필요",
      "comment_deadline": "2026-09-29",     // ★의견제출 마감 — 알림 트리거★
      "linked_issue_id": "2026-W35-battery-act"
    }
  ]
}
```

**행정예고 대응 워크플로 (요구사항 C4의 핵심)**

```
법령 예고 감지 (law-watch, 매 2시간)
  ↓
① affects_futurem 판정 — 적용대상·품목·의무 사전 매칭 (L0 규칙)
  ↓ true
② 조문 단위 요약 + 당사 영향 분석 (L2)
   "제12조 세제지원 대상에 양극재는 포함, 음극재는 미포함"
  ↓
③ 퓨처엠 기준 SWOT + 의견제출 초안 (L2)
   → response.policy_ask = "제12조 적용대상에 음극재 추가 요청"
  ↓
④ ★의견제출 마감 D-14 / D-7 / D-3 알림★
   예고기간을 놓치면 대응 기회 자체가 사라진다
  ↓
⑤ 웹 /policy/ 법령 탭 + 메일 Part B + (포스코 언급 시) 카톡
```

> 💡 **`comment_deadline` 알림이 이 트랙에서 가장 실용적인 기능이다.** 행정예고는 통상 20~40일인데, 그 기간을 놓치면 의견을 낼 수 없다. 대외협력 업무에서 이 알림 하나가 시스템 전체 값어치를 할 수 있다.

#### 4.1.5 공통 네거티브 필터

> 💡 **정책·통상 트랙의 핵심 가치는 "예고 단계 포착"이다.** 시행 후 기사로 아는 것과, 입법예고·Federal Register 공고 단계에서 아는 것은 대응 시간이 수 주 차이 난다. 이것이 T3를 뉴스만으로 채우지 않는 이유다.

```yaml
negative_keywords: [테마주, 리딩방, 상한가, 급등주, 채용공고, 주가 전망, 목표주가]
negative_outlets: [<광고성 매체 리스트 — 운영하며 축적>]
negative_patterns:
  - "^\\[부고\\]"
  - "^\\[인사\\]"          # 단, T1은 인사 기사 유지 (그룹 인사는 대외협력 관심사)
  - "^\\[포토\\]"
  - "증권가 소식"
```

| 구글 뉴스 RSS (국문) | `news.google.com/rss/search?q=&hl=ko&gl=KR&ceid=KR:ko` | 비공식·무제한 | **429/블록 시 T2·T3 해외분 손실** → §13-P1-3 |
| 구글 뉴스 RSS (영문) | 동일, `hl=en&gl=US&ceid=US:en` | 동일 | 동일 |
| Google CSE | Custom Search JSON API | 일 100 | 정밀 보강용 (선택) |
| 정부/기관 RSS | 각 사이트 | — | 개별 실패 허용(fail-soft) |

> ⚠️ 네이버 뉴스 페이지 직접 스크래핑은 약관/robots 이슈가 있어 **검색 API 사용을 원칙**으로 한다. 본문은 §F-02와 같이 언론사 원문 URL에서 가져온다.

### F-02. 정규화 · 중복제거 · 사전 게이트 (Normalizer)

**출력:** `raw/<run_id>/normalized.jsonl`

#### 4.2.1 기사 ID 생성 (v1.0 변경)

```python
# v0.2: f"{date}-{slugify(title)}"  ← 제목 수정 시 id 변경 → 즐겨찾기·이슈 참조 파손
# v1.0:
article_id = f"{date}-{sha1(canonical_url)[:10]}"
# 예: "2026-08-26-a3f9c1d2e8"
```

- 원문 URL이 정본(canonical). 트래킹 파라미터(`utm_*`, `sid`, `ref`) 제거 후 해시
- 같은 기사가 네이버·구글 양쪽에서 잡혀도 동일 id로 수렴
- `title_slug`는 사람이 읽는 용도로 별도 필드에 보관 (URL 경로에는 `id` 사용)

#### 4.2.2 중복 제거 3단계

| 단계 | 방법 | 처리 |
|---|---|---|
| L1 URL | canonical URL 완전 일치 | 병합 (`sources[]`에 소스 누적) |
| L2 제목 | 정규화 후 유사도 ≥ 0.9 (SimHash / 자카드) | 대표 1건 선정, 나머지 `dedup_of` |
| L3 본문 | 크롤링 후 본문 SimHash ≥ 0.85 (통신사 전재) | 대표 1건 선정 |

**대표 기사 선정 기준:** ① 원 통신사(연합·뉴시스) > ② 매체 티어 상위 > ③ 발행 시각 빠름
**⚠️ 주의:** 대표 기사가 일일 상한에 걸려 탈락하면 `dedup_of` 포인터가 끊긴다 → **대표 기사는 상한 컷에서 면제**한다. (§12 검증 2회차)

#### 4.2.3 사전 스코어 & 일일 상한 (v1.0 신규 — 순서 결함 수정)

> **문제:** v0.2는 "카테고리별 일일 상한 + `impact` 컷"이라고 썼는데, `impact`는 LLM 분석 **후**에 생기는 값이다. 분석 전에 컷하려면 분석 없이 계산 가능한 점수가 필요하다. (§12 검증 2회차)

```python
prescore = (
    outlet_tier_weight        # 티어1 매체 3.0 / 티어2 2.0 / 기타 1.0
  + keyword_weight            # must 키워드 히트 2.0, expand 1.0 (합산, 상한 4.0)
  + posco_string_hit * 3.0    # 포스코 문자열 등장 (강한 가중)
  + recency_weight            # 6시간 이내 1.0
  - duplicate_penalty         # 유사 기사 다수 존재 시 감점
)
```

**2단계 컷 구조**

```
수집 (예: 340건)
  → 네거티브 필터            → 280건
  → dedup L1·L2              → 165건
  → prescore 정렬 후 카테고리별 상한 적용 → 110건   ← [사전 컷]
     · 단, posco_string_hit 기사는 상한 면제
     · 단, 전재 대표 기사는 상한 면제
  → FETCH + ANALYZE (110건)
  → dedup L3 (본문 기준)     → 98건
  → impact=low AND track!=posco 인 기사는 카드 노출은 하되
     '더보기' 접힘 처리                              ← [사후 컷]
```

#### 4.2.4 트랙 판정 및 `posco_relevance` 1차 판정

- `track` — §1.3 경계 판정 규칙 적용 (룰 기반 1차 → S4c에서 LLM 검증)
- `posco_relevance` — 문자열 매칭으로 후보만 추출, 최종 판정은 S4c

### F-03. 본문 크롤링 (Fetcher)

**적용 대상:** T1·T2·T3 **전 기사 동일** (INV-1)
**출력:** `cache/<url_hash>.json` — `{url, fetched_at, title, body, byline, published_at, outlet, lang}`
**저장 위치:** **PRIVATE repo 또는 로컬** (public repo 저장 금지 — INV-5)

- 추출 엔진: `trafilatura`(1순위) → `readability-lxml` → `newspaper3k`
- **robots.txt 준수**, User-Agent 명시, **도메인별 요청 큐 + 간격 ≥ 1.5초**
- 동시성: 전역 8, 도메인별 1
- 실패 시: 검색 API `description` 스니펫으로 degrade → `crawl_status: partial`
- 페이월 감지(본문 <300자 + 로그인 키워드) → `paywall: true`, 제목·링크만
- PDF 리포트: `pdfplumber`로 텍스트 추출 (기관 리포트 대응)
- 영문 기사: 본문 원문 저장, **요약은 한국어로 생성** (`lang: en`, `summary_lang: ko`)
- 캐시 TTL 90일, 만료 시 자동 삭제

> 🔒 **저작권 원칙:** 본문 전문은 **비공개 캐시에만** 저장하고, 웹·카톡·텔레그램에는 **자체 작성 요약문 + 원문 링크**만 게시한다. 원문 인용은 문장당 1개, 짧게. 단, **공공누리 적용 정부 보도자료는 예외**로 전문 인용 가능(출처 표기).

### F-04. 요약 & 분석 (Analyzer)

기사 1건당 아래 필드를 생성한다. **T1·T2·T3 구분 없이 동일 적용** (INV-1).

| 필드 | 생성 에이전트 | 설명 | 공개여부 |
|---|---|---|---|
| `summary` | S4a | 카드용 1~2문장 | 🌐 공개 |
| `bullets[]` | S4a | 핵심 포인트 3~5개 | 🌐 공개 |
| `tone` | S4b | `positive`/`neutral`/`negative`/`crisis` | 🌐 공개 |
| `tone_evidence` | S4b | 논조 판정 근거 문장 지목 | 🔒 비공개 |
| `impact` | S4b | `high`/`mid`/`low` | 🌐 공개 |
| `track` / `also_tracks[]` | S4c | 트랙 (LLM 검증) | 🌐 공개 |
| `companies[]` | S4c | 언급 기업 (그룹사+타사) | 🌐 공개 |
| `countries[]` | S4c | 관련 국가 (T3 필수) | 🌐 공개 |
| `topics[]` | S4c | 이슈 태그 | 🌐 공개 |
| `facets[]` | S4c | **통합 필터 키** = companies + countries + topics | 🌐 공개 |
| `posco_relevance` | S4c | `primary`/`mention`/`none` ← 카톡 게이트 | 🌐 공개 |
| `frame` | S4c | 기사가 채택한 프레임 1줄 | 🔒 비공개 |
| `sector_impact` | S4d | `direct`/`indirect`/`none` — 포스코 미언급이어도 산업 영향도 | 🔒 비공개 |
| `futurem_implication` | S4d | 퓨처엠 관점 시사점 1~2문장 | 🔒 비공개 |
| `swot_axis` | S4d | `S`/`W`/`O`/`T`/`-` | 🔒 비공개 |
| `policy_ask_hint` | S4d | T3 전용 — 정부 건의 포인트 씨앗 | 🔒 비공개 |
| `fact_check_flags[]` | S4e | 사실관계 확인 필요 지점 | 🔒 비공개 |

> **공개/비공개 구분이 v1.0의 핵심 변경이다.** `futurem_implication`과 `swot_axis`는 사실상 SWOT 분석의 파편이다. 이걸 public `articles.json`에 넣으면 SWOT을 private repo로 옮긴 의미가 없어진다. (§12 검증 3회차)

#### 4.4.1 `posco_relevance` 판정 규칙 (카톡 발송 게이트)

| 값 | 정의 | 판정 방법 | 카톡 |
|---|---|---|---|
| `primary` | 포스코 계열사가 기사의 **주제** | 제목에 계열사명 OR 본문 3회 이상 | ✅ 항상 |
| `mention` | 포스코가 **비교군·인용**으로 언급 | 본문 1~2회, 제목엔 없음 | ✅ `impact ≥ mid` |
| `none` | 미언급 | 계열사명 미등장 | ❌ 웹·텔레그램만 |

**2단계 판정:** ① 문자열 매칭으로 후보 추출 → ② Claude가 맥락 검증
→ *"국내 배터리 3사와 포스코퓨처엠 등"* 같은 단순 나열, 시세표·종목 리스트 언급은 `none`으로 강등한다. 문자열만 쓰면 카톡이 스팸이 된다.

#### 4.4.2 `sector_impact` (v1.0 신규)

정책 트랙 때문에 필요해진 필드다. 예: *"美 45X 음극재 적격비용 축소"* 는 포스코를 한 번도 언급하지 않지만 **직격탄**이다. `posco_relevance=none` 이지만 `sector_impact=direct`.

| 값 | 정의 | 용도 |
|---|---|---|
| `direct` | 퓨처엠 사업에 직접 영향 (제품·원료·고객·규제 대상) | 웹 상단 고정, 텔레그램 긴급, SWOT 우선 |
| `indirect` | 산업 전반 영향, 퓨처엠에 2차 파급 | 일반 노출 |
| `none` | 참고 수준 | 접힘 노출 |

> ⚠️ **`sector_impact`는 카톡 게이트에 사용하지 않는다.** 사용자 요구사항(INV-4)은 "포스코가 언급되어 있으면 카톡 송부"이므로 게이트는 `posco_relevance` 단독이다. 다만 이 때문에 *"우리에게 가장 중요한 정책 기사가 카톡에 안 뜨는"* 상황이 발생한다 → **§13-P0-2 결정 필요**.

#### 4.4.3 논조 판정 기준

- `crisis`: 안전사고·법적분쟁·규제제재·오너리스크 등 즉시 대응 필요
- `negative`: 실적·경쟁력·평판에 부정적 서술이 주된 논지
- `neutral`: 사실 전달, 단순 실적/공시/인사/정책 발표
- `positive`: 수주·기술성과·정책수혜

> **T2·T3 기사의 논조는 "기사 자체의 논조"를 판정한다.** 경쟁사 호재는 기사 논조 `positive`이고, 우리 입장의 위협은 `swot_axis=T`로 표현한다. 두 개념을 섞으면 경쟁사 호재 기사가 전부 `negative`로 라벨링돼 통계가 무의미해진다.

#### 4.4.4 중요도(impact) 판정

```
high =
    tone == crisis
 OR (posco_relevance == primary AND tone == negative AND outlet_tier <= 2)
 OR (track == battery AND 밸류체인 구조 변화급: 대형 증설·기술 상용화·대형 수주)
 OR (track == policy AND sector_impact == direct AND 확정/시행/개정 단계)
```

**정책 단계 가중 (T3 전용)** — 같은 주제라도 단계에 따라 중요도가 다르다.

| 단계 | 코드 | 가중 |
|---|---|---|
| 논의·검토 | `discussion` | 낮음 |
| 입법예고·공고 | `proposed` | **높음 (선제 대응 기회)** |
| 확정·공포 | `enacted` | 높음 |
| 시행 | `effective` | 중간 |
| 개정·폐지 | `amended` | 높음 |

### F-05. SWOT & 대응방안 — **포스코퓨처엠 기준 고정**

> 🎯 **기준점:** 모든 SWOT은 **포스코퓨처엠 관점**. 포스코홀딩스 기사든 CATL 기사든 EU 규정 기사든, 최종 질문은 항상 **"이것이 포스코퓨처엠에게 무엇인가"**.
> 🖥️ **노출:** **웹에서만.** 카카오톡·텔레그램 메시지에 SWOT 문구를 절대 포함하지 않는다 (INV-3).
> 🔐 **저장:** **PRIVATE repo** (§3.2).

#### 4.5.0 기사 단위 SWOT vs 이슈 단위 SWOT (v2.0 명확화)

> **요구사항 C2는 "[기사] SWOT 분석"이다.** 그런데 기사 1건마다 4분면 SWOT을 만들면 같은 내용이 12번 반복되고 품질이 무너진다. 실제로 기사 12건은 대개 이슈 3개다.
> → **두 층위로 나눠 둘 다 제공한다.**

| 층위 | 산출 | 어디에 | 갱신 |
|---|---|---|---|
| **기사 단위** | `swot_axis` (S/W/O/T 중 1개) + `futurem_implication` 1~2문장 | 기사 카드·상세 | 기사 분석 시 즉시 |
| **이슈 단위** | 4분면 전체 + 교차전략(SO/ST/WO/WT) + 대응방안 + `policy_ask` | `/swot/` (L2) | 일 1회 + 주간 재구성 |

**기사 카드에서 보이는 모습**

```
🔴 부정   중요도 상   [T 위협]        ← swot_axis 배지
포스코퓨처엠, 3분기 양극재 가동률 60%대로
...
💡 당사 영향  [T 위협]                ← futurem_implication (L2 세션에서만)
고객사 재고조정이 장기화되면 단결정 전환 투자
회수 시점이 밀릴 수 있습니다.
              [이 이슈 SWOT 전체 보기 ▸]   ← 이슈 단위로 연결
```

> 사용자가 기사를 볼 때는 **"이게 우리한테 기회냐 위협이냐"** 만 알면 되고, 4분면 전체는 이슈 화면에서 본다. 요구사항 C2와 C3를 동시에 만족하는 구조다.

#### 4.5.1 프로세스

```
1. 대상 기사 집합 = 최근 14일 (T1+T2+T3 혼합)
2. 클러스터링
   a. 1차: topics/facets 자카드 유사도로 후보 그룹 생성
   b. 2차: Claude가 그룹을 검토해 이슈 제목 부여 + 병합/분할
   c. 기존 open 이슈와 매칭 → 신규 이슈만 생성 (id 안정성)
3. 이슈별 퓨처엠 관점 SWOT + 교차전략 + 대응방안 생성
4. private repo issues.json 저장 → /swot/ 렌더
```

**⚠️ 이슈 ID 안정성 (v1.0 수정):** v0.2는 daily가 `issue_id`를 붙이고 weekly가 클러스터를 재생성해 **id가 매주 바뀌었다**. `articles.json`의 `issue_id` 참조가 끊긴다. → **이슈 id는 최초 생성 시 확정하고(`YYYY-Www-슬러그`), 이후 재클러스터링은 기존 이슈에 기사를 추가하는 방식**으로만 동작한다. 이슈 병합 시 `merged_into` 포인터를 남긴다. (§12 검증 2회차)

#### 4.5.2 축 정의 (프롬프트에 그대로 삽입)

| 축 | 정의 | 요인 위치 |
|---|---|---|
| **S** Strength | 포스코퓨처엠이 이미 보유한 역량·자산 | **내부** |
| **W** Weakness | 포스코퓨처엠이 부족하거나 취약한 지점 | **내부** |
| **O** Opportunity | 외부 환경 변화 중 퓨처엠에 유리한 것 | **외부** |
| **T** Threat | 외부 환경 변화 중 퓨처엠에 불리한 것 | **외부** |

> ⚠️ 최빈 오류: **경쟁사 강점을 `S`에 쓰는 것.** S/W는 오직 포스코퓨처엠의 것이고, 경쟁사·정부·시장 동향은 전부 `O` 또는 `T`다.
> ⚠️ 2위 오류: **정책을 무조건 `T`로 쓰는 것.** 규제 강화가 중국 경쟁사에 더 불리하면 그것은 퓨처엠에겐 `O`다. 프롬프트에 "상대적 유불리를 따지라"고 명시한다.

#### 4.5.3 산출 스키마

```yaml
issue_id: "2026-W35-us-45x-amendment"

```

```
   부과국 × 대상국 매트릭스 — 셀에 최신 단계 + 관세율
   ┌──────────┬──────────┬──────────┬──────────┐

   │ 🇺🇸 미국  │ [발효]25%│ [발효]사실상│[협상중]🔴│
   │ 🇨🇦 캐나다│ —        │ [발효]100%│ —        │

   각 노드에 날짜·관세율·근거 기사

   퓨처엠 수출입 품목(양극재·음극재·전구체·흑연)에 걸리는 조치만 필터

④ 기사 카드 그리드
   부과국·대상국·품목·단계·기간 필터
```

**데이터:** `private/data/disputes.json` — 정책과 동일하게 **분쟁을 엔티티로 관리**하고 기사를 상태 변화 이벤트로 붙인다.

#### 4.6.8 기존 `/trade/` 페이지 처리 → P2-1 해소 (v1.2)

v1.0에서 미결로 남겨둔 **기존 `나라별 통상정책 현황` 페이지와의 중복** 문제는, 신규 T4 탭이 같은 주소를 쓰면서 자연스럽게 해소된다.

**확정: A안(흡수).** 기존 수기 큐레이션 내용을 `disputes.json`의 초기 시드로 이관하고, 이후는 자동 수집이 타임라인을 이어 붙인다. 기존 URL은 그대로 유지되므로 리다이렉트도 불필요하다.

### F-10. 발송 라우팅 — 지정 톡방 선별 송부 (v1.2 신규)

> **요구사항:** 통상·규제 기사는 팀 전체 단체방이 아니라 **내가 지정한 톡방에만** 보낸다.

#### 4.10.1 설계 원칙

v1.1까지 발송 규칙은 `should_send_kakao()` 함수 하나에 하드코딩돼 있었다. 톡방이 둘 이상이 되는 순간 이 구조는 무너진다.
→ **발송 대상(방)과 발송 조건을 설정 파일로 분리**한다. 코드 수정 없이 방을 추가·변경할 수 있어야 한다.

#### 4.10.2 `pipeline/dispatch_routes.yaml`


#### 4.10.3 발송 관리 패널 (v2.1 역할 재정의)

> **Plan B 채택으로 이 패널은 "매일 쓰는 도구"에서 "가끔 쓰는 관리 도구"가 됐다.** 상시 발송은 자동이고, 패널은 예외 상황을 다룬다.

| 용도 | 시점 |
|---|---|
| **킬 스위치 토글** | 사고 시 즉시 발송 중단 |
| **보류 건 검토·승인** | 이상 감지에 걸린 건(특히 `crisis`)을 사람이 보고 발송/폐기 결정 |
| **수동 발송** | 자동에서 빠졌지만 공유해야 할 기사 |
| **재발송** | API 실패로 누락된 건 |
| **발송 이력 조회** | 무엇이 언제 나갔는지 |
| 복사 발송 (폴백) | 카카오 API 장애 시 아래 흐름으로 수동 전송 |

**폴백 복사 흐름 (API 장애 시에만)**

카드형은 기사당 **링크 → 요약** 순으로 **두 번 붙여넣어야** 한다. 클립보드는 한 번에 하나뿐이므로, 단순 "복사" 버튼으로는 운영이 불가능하다.
→ 웹에 **발송 모드 패널**을 둔다.

```
┌─ 📤 카톡 발송 모드 · 8/26(수) · 6건 ─────────────┐
│                                                   │
│  진행  ●●●○○○   3/6                              │
│                                                   │
│  ④ [뉴스토마토] 미·캐나다 '관세전쟁' 불똥?…       │
│                                                   │
│   STEP 1  링크                                    │
│   ┌───────────────────────────────────────────┐  │
│   │ https://www.newstomato.com/...            │  │
│   └───────────────────────────────────────────┘  │
│                          [📋 복사하고 다음 →]     │
│                                                   │
│   STEP 2  요약  (STEP 1 복사 후 활성화)           │
│   ┌───────────────────────────────────────────┐  │
│   │ [뉴스토마토] 캐나다에 현지 생산 기반을...  │  │
│   └───────────────────────────────────────────┘  │
│                          [📋 복사하고 다음 →]     │
│                                                   │
│  [◀ 이전]                    [건너뛰기]  [완료]   │
└───────────────────────────────────────────────────┘
```

**동작**
- `[복사하고 다음]` → 클립보드 복사 + 자동으로 다음 STEP/기사로 이동 → **버튼만 반복 탭하면 되는 흐름**
- 각 복사 시각을 `dispatch_log`에 기록 → 재진입 시 `이미 09:12에 발송함` 경고
- `[건너뛰기]` — 담당자 판단으로 특정 기사 제외 (사유 선택 시 다음날 필터 개선에 반영)
- 모바일에서도 동작해야 한다. 출근길에 폰으로 붙여넣는 경우가 많다
- 요약 텍스트는 **편집 가능**하게 둔다. 자동 생성 문장을 사람이 다듬고 보내는 것이 현실적이다

> Plan B(오픈채팅 API)로 전환하면 이 패널은 그대로 두되 `[전체 자동 발송]` 버튼이 추가된다. `filter`·`format` 정의는 재사용된다.

### F-11. 일일 브리핑 메일 (v1.3 개정 — 2부 구성)

> **요구사항 (v1.3 갱신):**
> ① 전날 포스코 관련 기사를 **어느 업체에서 어떤 내용으로 보도했는지** 정리해 발송 → **Part A**
> ② T3·T4(정책·통상) 중 포스코 미언급분은 카톡 대신 **메일로만** 전달 → **Part B**
> ③ 발송 시각 **07:00**
> ④ 사외 계정에서 **사내 단체 메일(배포 리스트)** 로 발송

#### 4.11.1 이 기능의 성격

카톡·텔레그램 브리핑과 목적이 다르다. 브리핑은 *"무슨 일이 있었나"* 이고, 클리핑 메일은 **"어느 매체가 우리를 어떻게 다뤘나"** 다. 대외협력 관점에서는 후자가 더 중요할 때가 많다. 같은 사안을 A매체는 우호적으로, B매체는 비판적으로 쓴다면 그 차이 자체가 대응 정보다.

→ 따라서 **정렬 기준이 시간이 아니라 언론사**다.

**Part A / Part B 구분 기준**

| | Part A | Part B |
|---|---|---|
| 대상 | `posco_relevance ∈ {primary, mention}` | `track ∈ {policy, trade}` **AND** `posco_relevance = none` **AND** `impact ≥ mid` |
| 정렬 | **언론사별** | **트랙·카테고리별** |
| 관심사 | "누가 우리를 어떻게 썼나" | "무슨 제도·조치가 어느 단계인가" |
| 표시 | 논조 배지, 매체별 대비 | 국가 플래그, 단계 배지, 품목 해당 여부 |
| 카톡 중복 | 있음 (같은 기사가 카톡에도) | **없음 — 메일에서만 볼 수 있는 내용** |

> Part B는 **카톡에 안 가는 내용**이므로, 메일을 안 읽으면 아예 못 본다. 그래서 제목에 건수를 노출한다: `[포스코 브리핑] 8/26(수) 포스코 12건 · 정책통상 8건`

- **④ 대비 섹션**은 같은 `issue_id`에 2개 이상 매체가 붙었을 때만 생성한다
- 요약은 **자체 작성 문장 + 원문 링크**만 싣는다. 기사 본문 전재 금지 (§9.2)
- **SWOT·`policy_ask`·`futurem_implication`·`frame`은 싣지 않는다 (INV-7)**

#### 4.11.3 대상 범위 (결정 필요 항목 있음)

| 항목 | 기본값 | 비고 |
|---|---|---|
| 대상 기사 | Part A: `posco_relevance ≠ none` / Part B: 정책·통상 미언급분 | Part A는 카톡과 동일 기준 |
| 기간 | 전일 00:00~24:00 | 카톡 브리핑(07:00 기준 24시간)과 경계가 다름 → §13 P1-8 |
| 발송 시각 | **07:00** | 야간 배치로 전일분을 미리 완성해 두고 **발송만** 수행 (§6.4) |
| 수신자 | `MAIL_TO_GROUP` — **사내 배포 리스트 주소 1개** | §F-11.6 참조 |
| 포맷 | HTML + 텍스트 폴백 | 사내 메일 클라이언트 호환 |

#### 4.11.4 품질 폴백 (논조 미확정 시)

논조(`tone`)는 L1·L2 산출물이다. PC가 꺼져 있어 야간 배치가 L0에서 멈추면 논조 칸이 비어 있다.

```
06:40  L1·L2 완료 여부 확인
  ├─ 완료   → 논조·매체별 대비 포함 전체 포맷으로 발송
  └─ 미완료 → 셀프호스트 재시도 1회 (10분)
       ├─ 성공 → 전체 포맷
       └─ 실패 → ★논조 열·Part A ④(매체별 대비) 제외★
                  "언론사별 보도 목록" 형태로 07:00 정시 발송
```

**메일을 거르지 않는다 (INV-6).** 논조 없는 목록만으로도 "어느 매체가 몇 건 썼는지"는 전달되고, 그게 이 메일의 최소 가치다. 이 경우 제목에 `(요약본)`을 붙여 구분한다.

#### 4.11.5 발송 구현 (API 키 불요)

```python
SMTP_HOST = "smtp.gmail.com"; SMTP_PORT = 587   # 개인/사외 Gmail + 앱 비밀번호
# 사내 릴레이 사용 가능 시 사내 SMTP 주소로 교체 (권장)
```

- 발송은 **클라우드 러너에서도 가능**하다 (SMTP는 로컬 PC 불필요)
- 발송 성공/실패를 `dispatch_log`에 기록. 실패 시 텔레그램 `#운영-알림` 통지
- **Bounce 수신 처리**: 배포 리스트가 반송되면 조용히 실패한다. 반송 메일함을 주 1회 확인하거나, 발신 계정 자신을 `Bcc`에 넣어 **도달 여부를 자가 확인**한다

#### 4.11.6 사외 → 사내 단체 메일 발송 검토 (v1.3 신규)

**질문:** 수신자 10명 이하가 아니라 **단체 메일(배포 리스트)로 묶으면 가능한가?**
**답:** **발송 한도 문제는 완전히 해결된다.** 다만 병목이 다른 곳으로 옮겨간다.

**① 발송 한도 — 해결됨 ✅**

배포 리스트 주소 1개로 보내면 **발신자 입장에서 수신자는 1명**이다. 팬아웃은 수신 측 그룹 서버가 처리한다.

| 항목 | 수치 | 우리 사용량 |
|---|---|---|
| 개인 Gmail 일일 발송 | 500통 (24시간 롤링) | **1통/일** |
| Google Workspace 일일 발송 | 2,000통 | 동일 |
| **SMTP 경유 메시지당 수신자** | **100명** ← 실질 제약 | **1명 (그룹 주소)** |

> Gmail 공식 문서도 한도 초과를 피하는 방법으로 **"모든 수신자를 포함한 그룹을 만들어 그룹 주소로 전송"** 을 안내한다. 우리 방식이 정확히 그것이다.
> ⚠️ **`Bcc`에 수십 명을 넣는 방식은 쓰지 말 것.** 수신자 수가 그대로 카운트되고 스팸 점수도 올라간다. 배포 리스트가 모든 면에서 낫다.

**② 진짜 병목 — 사내 수신 정책 ⚠️**

발송이 아니라 **수신 쪽에서 막힌다.** 대부분의 조직은 사내 배포 리스트를 내부 전용으로 잠가 둔다.

| 관문 | 확인 사항 | 막히면 |
|---|---|---|
| **배포 리스트 외부 수신 허용** | 그룹 주소가 외부 발신자 메일을 받도록 설정돼 있는가 | 발신자 주소를 그룹 허용 목록에 등록 요청 |
| **메일 보안 게이트웨이** | 외부에서 오는 자동화·정기 메일을 격리하는가 | 발신 주소 화이트리스트 등록 요청 |
| **SPF / DKIM / DMARC** | Gmail 발신은 gmail.com 도메인으로 인증되므로 통과 가능 | 자체 도메인 사용 시 DNS 설정 필요 |
| **사내 정보보호 정책** | 외부 계정에서 사내 다수에게 정기 발송이 허용되는가 | 사내 계정 발신으로 전환 |

**③ 권장 순서**

| 순위 | 방식 | 장단 |
|---|---|---|
| **1** | **사내 계정에서 발신** (사내 SMTP 릴레이 / Exchange) | 사내→사내라 필터 통과가 가장 쉽다. **가능하면 이걸로** |
| 2 | 사외 Gmail 발신 + 배포 리스트 + **화이트리스트 등록** | IT 협조 1회면 안정적 |
| 3 | 사외 Gmail 발신 + 배포 리스트 (등록 없이) | 초기엔 되다가 스팸 학습으로 막힐 수 있음 |
| 4 | 사외 Gmail + 개별 수신자 20명 이하 | 관리 부담, 인원 변동 시 수정 필요 |
| 5 | 메일 포기 → **텔레그램 `#브리핑` 채널** | 포맷만 바꾸면 되므로 구현 비용 거의 0 |

**④ 도달률을 위한 기술 조치**

| 항목 | 조치 |
|---|---|
| 제목 접두어 고정 | `[포스코 브리핑]` — 사내 규칙 필터로 폴더 자동 분류 유도 |
| `List-Id` 헤더 | `List-Id: posco-news.internal` — 자동 발송임을 명시해 필터가 뉴스레터로 분류하게 |
| `List-Unsubscribe` 헤더 | 수신 거부 경로 제공 (스팸 점수 하락) |
| 발신 전용 계정 분리 | 개인 업무 메일과 섞지 않는다. 한쪽이 막혀도 다른 쪽 영향 없음 |
| multipart | HTML + 텍스트 폴백 동시 제공 |
| 링크 | 단축 URL 금지, 도메인 최소화, 링크 대비 텍스트 비중 유지 |
| 이미지·첨부 | **없음** — 썸네일 이미지도 넣지 않는다. 첨부는 스팸 점수와 사내 검역에 가장 취약 |
| 발송 리듬 | 매일 같은 시각 1통. 갑작스러운 다중 발송 금지 |

**⑤ 초기 검증 절차**

```
1주차: 본인 사내 주소로만 발송 → 스팸함 여부 확인
2주차: 팀원 2~3명 추가 → 도달 확인
3주차: 배포 리스트 전환 → 반송·격리 확인
   ↳ 이 단계에서 막히면 IT에 화이트리스트 등록 요청
```

> 처음부터 배포 리스트로 쏘면 **한 번의 스팸 신고로 발신 계정이 통째로 차단**될 수 있다. 단계적으로 올린다.

### F-13. 주간 브리프 (v2.0 신규 — 요구사항 E5·E6)

> **요구사항:** *"월요일에 주간 기사 내용 요약 및 향후 대응 방안 예측"*

**실행:** 월요일 07:30 (셀프호스트 · L2) → 메일 + 웹 `/weekly/`

#### 4.13.1 구성

```
[주간 브리프] 2026-W35 (8/19~8/25)

① 한 주 요약
   총 214건 · 포스코 68 · 산업 92 · 정책 34 · 통상 20
   논조: 긍정 41 / 중립 132 / 부정 39 / 위기 2
   전주 대비: 부정 +12건 ▲   ← 추세가 핵심

② 이번 주 핵심 이슈 (3~5개)
   각 이슈: 기사 수 · 논조 분포 · 퓨처엠 기준 SWOT 요약 · 대응 상태

③ 매체 동향
   우리를 가장 많이 다룬 매체 / 논조가 부정으로 기운 매체
   → 프레임 변화 감지

④ 법령·정책 캘린더 ★
   · 의견제출 마감 임박: 이차전지 특별법 시행령 (D-9)
   · 시행 예정: 화관법 개정 시행 (10/1)
   · 예고 신규: 2건

⑤ 향후 전망 (outlook) ★요구사항 E6★
```

#### 4.13.2 `outlook` — 향후 대응 방안 예측

> ⚠️ **예측은 할루시네이션이 가장 잘 나오는 영역이다.** "예측"을 자유롭게 시키면 그럴듯한 창작이 나온다. 그래서 **근거가 있는 것만, 신뢰도를 붙여서** 생성한다.

```yaml
outlook:
  scheduled:                    # ★확정된 일정 — 예측이 아니라 사실★
    - date: "2026-09-29"
      event: "이차전지 특별법 시행령 의견제출 마감"
      action: "제12조 음극재 포함 의견서 제출"
      confidence: certain
  likely:                       # 근거 있는 전개
    - text: "45X 개정안 의견수렴이 10월 종료되면 연내 최종규칙 공표 가능성"
      basis: ["2026-08-26-a3f9c1d2e8"]     # ★근거 기사 필수★
      confidence: medium
      watch: "Federal Register 최종규칙 공고"
  monitoring:                   # 근거는 약하나 주시 필요
    - text: "중국 흑연 수출통제 품목 추가 여부"
      basis: []
      confidence: low
  recommended_actions:          # 대응방안 초안 (요구사항 C7)
    - "① 9월 2주까지 제12조 의견서 초안 완료"
    - "② 북미 원가 데이터 체계 점검 착수"
```

**생성 규칙 (프롬프트에 명시)**

| 규칙 | 이유 |
|---|---|
| `scheduled`는 **날짜가 확정된 것만** | 여기에 추측이 섞이면 캘린더 전체를 못 믿는다 |
| `likely`는 **근거 기사 id 필수**, 없으면 `monitoring`으로 강등 | 근거 없는 예측 차단 |
| 수치 예측 금지 (가격·점유율·실적) | 검증 불가하고 틀리면 신뢰도가 무너진다 |
| `recommended_actions`는 **우리가 실제로 할 수 있는 행동**만 | "시장을 주시한다" 같은 문장 금지 |
| 전부 **L2 전용** | 대응방안은 내부 판단 (INV-3) |

> 메일에는 `scheduled`(사실)와 `recommended_actions` 중 **비민감 항목만** 싣고, `likely`·`monitoring`은 웹 `/weekly/`(L2)에서 본다.

### F-12. 인증 및 접근 제어 (v1.4 신규)

#### 4.12.1 Vercel 내장 Deployment Protection을 쓰지 않는 이유

먼저 검토했으나 **요건에 맞지 않는다.**

| 방식 | 문제 |
|---|---|
| **Vercel Authentication** (무료·전 플랜) | <cite index="16-1">이미 Vercel 팀에 로그인한 사람만 통과시킨다.</cite> 팀원 전원이 Vercel 계정을 만들고 팀 시트를 차지해야 한다 (Pro 기준 시트당 과금) |
| **Password Protection** | <cite index="12-1">Enterprise 플랜이거나 Pro에 월 $150 Advanced Deployment Protection 애드온이 필요하다.</cite> 연 $1,800 |
| **Standard Protection 범위** | <cite index="12-1">프리뷰와 생성된 배포 URL만 덮고 커스텀 프로덕션 도메인은 공개로 남는다.</cite> Hobby에서는 프로덕션 도메인을 아예 잠글 수 없다 |
| **Trusted IPs** | 사내망 IP만 허용 → 재택·모바일 불가. 상위 플랜 기능 |

**결정적 한계:** Deployment Protection은 **전부 아니면 전무**다. 우리는 L1(기사)과 L2(SWOT)를 **같은 사이트 안에서 다르게** 취급해야 한다. 배포 단위 보호로는 이게 불가능하다.

→ **앱 레벨 인증(Next.js middleware + 세션)** 을 직접 구현한다. 무료이고, 역할 분리가 되고, 감사 로그도 남는다.

#### 4.12.2 인증 방식 — 로그인 코드 (v1.5 변경)

| 방식 | 사내 협조 | 개인 식별 | 망분리 대응 | 판정 |
|---|---|---|---|---|
| ~~매직링크 (일회용 링크)~~ | 불필요 | ✅ | **❌ 기기를 건너뛴다** | v1.5에서 탈락 |
| **로그인 코드 (6자리 숫자)** | 불필요 | ✅ | ✅ | ✅ **채택** |
| SSO (Entra ID / Workspace OAuth) | **앱 등록 필요** | ✅ | ✅ | 사내 승인 나면 v2 전환 |
| 공유 비밀번호 + 서명 쿠키 | 불필요 | ❌ | ✅ | L2 부적합 (누가 SWOT을 봤는지 모름) |
| Vercel Authentication | 팀 시트 필요 | ✅ | ✅ | ❌ (§4.12.1) |

> ⚠️ **왜 매직링크가 탈락했는가 (망분리 때문):**
> 매직링크는 **메일을 여는 기기와 접속하는 기기가 같아야** 성립한다. 그런데 우리 상황은 정반대다.
> **메일은 Z1(사내 PC)에서 읽고, Vercel 접속은 Z3(모바일)에서 한다.**
> 사내 PC에서 링크를 눌러도 Vercel이 막혀 인증이 실패하고, URL을 휴대폰으로 옮겨 적는 것은 현실적이지 않다.
> **로그인 코드는 이 문제가 없다.** 사내 PC 메일에서 숫자 6자리를 보고 휴대폰에 입력하면 끝이다.

```
① 휴대폰 브라우저 /login 에서 사내 이메일 입력
② 도메인 화이트리스트 검증  ← 아니면 즉시 거절
③ 6자리 코드를 사내 메일로 발송 (10분 만료)
④ 사내 PC 메일함에서 코드 확인 → 휴대폰에 입력
⑤ 세션 쿠키 발급 (httpOnly, Secure, SameSite=Lax, 30일)
⑥ 이메일이 L2 허용목록에 있으면 role=admin
```

**코드 방식의 보안 보강 (숫자 6자리는 무차별 대입에 약하다)**

| 항목 | 값 |
|---|---|
| 만료 | 10분 |
| 시도 횟수 | **5회 실패 시 코드 폐기** + 재발급 필요 |
| 발급 제한 | 이메일당 5분 내 3회 |
| 일회성 | 성공 시 즉시 폐기, 재사용 불가 |
| 세션 고정 방지 | 코드 발급 시 브라우저에 논스를 심고 검증 시 대조 — **다른 기기에서 가로챈 코드로는 로그인 불가** |

**세션 정책**

| 항목 | 값 | 근거 |
|---|---|---|
| 유효기간 | **30일** | 카톡·메일 링크를 누를 때마다 로그인하면 아무도 안 쓴다 |
| 갱신 | 접속 시 슬라이딩 연장 | |
| L2 재확인 | `/swot/` 최초 진입 시 **재인증 없음**, 단 접근 로그 기록 | 마찰을 늘리면 안 쓰게 된다. 대신 감사로 통제 |
| 강제 만료 | 허용목록에서 제거 시 즉시 세션 무효 | 인사이동 대응 |

#### 4.12.3 링크 진입 UX

카톡·메일의 링크를 눌렀을 때 로그인 벽이 뜨는 흐름이 매끄러워야 한다.

```
[Z3 모바일] 카톡 링크 클릭
  → 세션 있음(30일) → 해당 기사로 바로 이동          ← 평상시 대부분
  → 세션 없음 → /login?next=/posco/articles/<id>
                코드 입력 후 ★원래 보려던 기사로 복귀★

[Z1 사내 PC] 메일의 `전체보기(로그인)` 클릭
  → Vercel 접속 가능 → 정상 동작
  → 차단 → ★메일 본문만으로 이미 업무가 된다 (INV-9)★
```

- `next` 파라미터는 **자체 경로만** 허용한다 (오픈 리다이렉트 방지)
- 카톡 메시지의 **OG 카드는 언론사 원문 링크**라 로그인과 무관하다. 로그인이 걸리는 건 `전체보기`뿐이고, 세션이 30일이라 실제로는 **한 달에 한 번 코드를 입력**하는 수준이다
- 메일 링크에는 `(로그인)` 표기를 붙여 Z1에서의 헛클릭을 줄인다

#### 4.12.4 API 응답 필드 필터링

```ts
// app/api/articles/route.ts
const L2_ONLY = ['futurem_implication','swot_axis','sector_impact',
                 'frame','tone_evidence','policy_ask_hint','fact_check_flags','body'];

export async function GET(req: Request) {
  const s = await getSession(req);
  if (!s) return new Response('Unauthorized', { status: 401 });

  const raw = JSON.parse(await fs.readFile('data/articles.json','utf8'));
  const articles = s.role === 'admin'
    ? withAnalysis(raw)                       // analysis.json 병합
    : raw.articles.map(a => omit(a, L2_ONLY)); // ★L1은 아예 안 내려보낸다★
  return Response.json({ ...raw, articles });
}
```

> **핵심:** L1에게는 L2 필드를 **응답에 담지 않는다.** 담아놓고 화면에서 숨기면 네트워크 탭에 그대로 보인다. INV-8의 실체가 이 코드다.

### F-07. 카카오톡 발송

> **⚠️ §9.1 제약사항을 먼저 읽을 것.** 기존 카카오톡 단체방으로 API 자동 발송하는 공식 경로는 없다.

#### 4.7.1 발송 게이트 (INV-4)

```python
def should_send_kakao(a) -> bool:
    if a.posco_relevance == "primary":
        return True
    if a.posco_relevance == "mention" and a.impact in ("high", "mid"):
        return True
    return False          # none → 웹/텔레그램만
```

- 트랙과 무관하다. T3 정책 기사여도 포스코가 유의미하게 언급되면 발송된다.
- 메시지에는 **요약·링크만**. SWOT·시사점·정책건의 미포함.
- **Fail-closed:** 게이트 판정에 필요한 필드가 없거나 오류면 **발송하지 않는다.** (§12 검증 5회차)

#### 4.7.2 발송 경로 옵션

|---|---|---|---|
| **A** | 카카오톡 채널 + 친구톡/알림톡 (비즈메시지) | ✅ 공식 | 유료·템플릿 심사·개인 수신 (단체방 아님) |

##### 메시지 1 — 카드 4요소 (전부 우리가 명시 지정)

| # | 요소 | 값 | 규칙 |
|---|---|---|---|
| ① | `thumbnail` | 기사 대표 이미지 URL | 원문 OG 이미지 **URL 참조**(재호스팅 금지). 없으면 **기본 썸네일** 사용 — 카드 형태는 절대 무너뜨리지 않는다 |
| ② | `title` | **기사 제목 원문 그대로** | 수정·요약·말줄임 금지. 매체가 붙인 따옴표·물음표 유지 |
| ③ | `description` | **기사 부제** | 부제가 없으면 `summary` 첫 문장을 40자 내로 절삭해 사용 (빈칸으로 두지 않는다) |
| ④ | `link` | **언론사 원문 URL** | 도메인이 카드 하단에 표시된다. 네이버 중계 링크보다 원문 우선, 단축 URL 금지 |

> 🔒 **OG 자동 미리보기에 의존하지 않는다.** URL만 던져 클라이언트가 렌더하게 두면 **매체마다 썸네일 유무·설명 길이가 제각각**이 되어 "형태 고정"이 깨진다. 네 요소를 전부 지정해 **어떤 매체의 기사든 동일한 카드**가 나오게 한다.

##### 메시지 2 — 요약 본문

| **본문** | 머리말에 이어 **한 문단**으로 연결. 의도적 줄바꿈 없음 (말풍선 자동 줄바꿈만) |

| 분량 | **3~5문장, 150~350자** |
| 구성 | ① 사안의 배경·현황 → ② 관련 기업의 구체적 상황 → ③ (있으면) 관전 포인트 |

| **절대 금지** | 이모지 · 불릿(`•` `└` `·`) · 해시태그 · 마크다운 · 논조 배지 · 중요도 표시 · URL |

| 폐기 | 사유 |

| ❌ 일일 요약·마무리 멘트 | 고정 형태에 없다 |

##### 발송 전 포맷 검증기 (Formatter Contract)

형태 고정은 **문서가 아니라 코드로 강제**한다. 아래를 통과하지 못한 건은 **발송하지 않는다**(fail-closed).

```python
BANNED = re.compile(r'[\U0001F300-\U0001FAFF\u2600-\u27BF]|^[•·\-└*]|#\w|\*\*|https?://')

def validate_kakao(card: dict, body: str) -> list[str]:
    e = []
    # 메시지 1 — 카드 4요소가 모두 있어야 한다
    for k in ('thumbnail', 'title', 'description', 'link'):
        if not card.get(k): e.append(f'card.{k} 누락')
    if card.get('link','').startswith(('http://bit.ly','https://bit.ly')): e.append('단축 URL')

    # 메시지 2 — 머리말·문체·분량·금지문자
    if not re.match(r'^\[[^\]]{2,12}\] \S', body):     e.append('[매체명] 머리말 형식 위반')
    if '\n' in body:                                    e.append('의도적 줄바꿈')
    if not (150 <= len(body) <= 350):                   e.append(f'분량 이탈 {len(body)}자')
    if BANNED.search(body):                             e.append('금지 문자(이모지/불릿/해시태그/URL)')
    if not body.rstrip().endswith('다.'):                e.append('존댓말 평서문 종결 아님')
    if not any(k in body for k in POSCO_ENTITIES):      e.append('포스코 언급 없음')
    return e
```

- 검증 실패 건은 **해당 기사만 제외**하고 나머지는 정상 발송한다 (전체 중단 금지)
- 실패 내역은 실행 리포트와 운영 채널로 통지 → `summarizer` 프롬프트 개선에 반영
- 이 검증기는 **회귀 테스트로 고정**한다. 예시 카드(뉴스토마토 건)를 골든 샘플로 저장해 CI에서 대조

| 상황 | 대응 |
|---|---|

| 기사 부제 없음 | `summary` 첫 문장 40자 절삭 (빈칸 금지) |

**② 발송 전 이상 감지 (Anomaly Guard)**

발송 직전에 아래를 검사하고, 하나라도 걸리면 **발송을 보류하고 담당자에게 알린다**.

| 조건 | 임계 | 조치 |
|---|---|---|
| 발송 건수 급증 | 평소 대비 3배 초과 | 보류 → 수동 확인 |
| 발송 건수 0 | 평일 0건 | 보류 → 파이프라인 이상 의심 |
| `tone=crisis` 포함 | 1건 이상 | **보류 → 반드시 사람이 먼저 본다** |
| `posco_relevance` 판정 실패 | 1건 이상 | 해당 건만 제외 (fail-closed, INV-4) |
| 요약 길이 이상 | 50자 미만 / 600자 초과 | 해당 건 제외 |
| 동일 URL 중복 | `dispatch_log` 히트 | 해당 건 제외 |

> **`crisis` 건을 자동 발송하지 않는 것이 특히 중요하다.** 안전사고·법적분쟁 기사는 홍보실 방침이 먼저 정해져야 하는 사안이다. 봇이 먼저 단체방에 뿌리면 곤란해진다.

**⑤ 발송량 상한**

```yaml
daily_limit: 8              # 카드+요약 = 최대 16메시지
burst_limit: 3              # 긴급 푸시는 시간당 3건까지
quiet_hours: ["22:00","07:00"]   # 야간 발송 금지, 다음 발송으로 이월
```

#### 4.7.6 오픈채팅방 운영 정책 (v2.1 신규)

오픈채팅은 일반 단체방과 성격이 다르다. **링크만 알면 외부인이 들어올 수 있다.** 사내 업무 정보가 오가는 방이므로 아래를 반드시 설정한다.

| 항목 | 설정 | 이유 |
|---|---|---|
| **입장 코드** | **필수 설정** | 링크 유출만으로 입장되는 것을 막는다 |
| **검색 노출** | **차단** | 오픈채팅 검색에 잡히지 않게 |
| 관리자 | 담당자 + 부관리자 1명 | 단독 관리는 부재 시 위험 |
| 정원 | 팀 인원 + 여유 소수 | 과다 설정 지양 |
| 프로필 | 실명 닉네임 권장 | 오픈채팅 기본은 익명 — 업무방에 부적합 |
| 정기 점검 | 월 1회 참여자 명단 확인 | 퇴사·이동자 정리 |

**이주 체크리스트**

- [ ] 카카오 오픈채팅 API 사용 신청 및 도메인 ID 발급 (심사 기간 있음 — **최우선**)
- [ ] API로 오픈채팅방 생성 → 입장 코드·검색 차단 설정
- [ ] 팀원 이주 안내 (기존 방에 링크 공지, 1~2주 병행 운영)
- [ ] 기존 단체방은 **아카이브 목적으로 유지** (오픈채팅은 이전 대화 이관 불가)
- [ ] 사내 보안정책상 오픈채팅 업무 사용 가능 여부 확인
- [ ] 봇 계정을 방 관리자로 지정

> ⚠️ **기존 단체방의 대화 히스토리는 옮겨지지 않는다.** 과거 공유 기사를 참조해야 한다면 기존 방을 지우지 말고 남겨 둔다.

### F-08. 텔레그램 발송 (Primary 자동 채널)

- 공식 **Telegram Bot API** — 그룹방에 봇 초대 후 `sendMessage`
- 기존 경제뉴스 텔레그램 봇 인프라(PM2 + Node) 재사용
- **채널 구성**

| 채널 | 대상 | 발송 |
|---|---|---|
| `#포스코-브리핑` | `posco_relevance ≥ mention` | 07:30 데일리 + 긴급 |
| `#산업-동향` | T2 전체 | 07:30 데일리 (선택 구독) |

### F-09. Q&A 챗봇

**동작 (RAG)**

```
질문 → ① 슬롯 추출(트랙/회사/국가/기간/논조/토픽, JSON 강제)
     → ② 검색: facets 필터 + BM25/임베딩 스코어 → 상위 8건
            (웹 인증 세션이면 issues.json 도 검색 대상)
     → ③ Claude 답변 생성 (후보 요약만 전달, 본문 전문 미전달)
     → ④ 출처 각주(기사 id + 링크) 포함 반환
```

**채널별 접근 범위**

| 채널 | articles | issues (SWOT) | 본문 캐시 |
|---|---|---|---|
| 웹 챗 위젯 (미인증) | ✅ | ❌ | ❌ |
| 웹 챗 위젯 (인증) | ✅ | ✅ | ✅ |

| **법령 영향** | "이차전지 특별법 예고안이 우리한테 어떤 영향이야?" |
| 원문 요약 | "이 링크 요약해줘" (즉석 크롤링) |

#### 4.9.5 법령 검색 기능 (v2.0 신규 — 요구사항 D2)

챗봇의 법령 질의는 **아카이브 RAG만으로는 답할 수 없다.** 수집된 기사에 없는 조문을 물어볼 수 있기 때문이다.

```
"폐기물관리법 배터리 재활용 조항"
  ↓
① 아카이브 검색 — laws.json에 해당 법령이 있는가
  ├─ 있음 → 엔티티 + 타임라인 + 당사 영향(L2) 반환
  └─ 없음 ↓
② 국가법령정보센터 API 실시간 조회 — 법령명·조문 검색
  ↓
③ 조문 원문 + 요약 반환 (조문은 공공저작물이라 인용 가능)
  ↓
④ L2 세션이면 "당사 영향" 분석을 덧붙임 (L2, on-demand)
```

**중요한 경계**

| 하는 것 | 하지 않는 것 |
|---|---|
| 조문 위치·내용 안내 | **법률 자문** |
| 시행일·예고기간 안내 | 위법 여부 판단 |
| 당사 사업과의 관련성 정리 | 법적 리스크 확정 진술 |

> 답변 하단에 **"법률 자문이 아니며 정확한 해석은 법무 부서·법률전문가 확인이 필요합니다"** 를 고정 표기한다. 법령은 조문 하나로 의무가 갈리는 영역이라 이 경계가 특히 중요하다.

**할루시네이션 방지 (시스템 프롬프트)**

- 아카이브에 근거가 없으면 추측 금지 → "수집된 기사에 없습니다"
- 모든 사실 주장에 기사 id/링크 각주
- 수치는 기사에 있는 것만 인용, 계산·추정 시 명시
- **메신저 채널에서는 SWOT·시사점·정책건의 문구 출력 금지** (프롬프트 + 후처리 필터 이중 차단)
- 정책 해석은 "법률 자문이 아님" 고지

### 6.3 실행 환경 (v1.1 확정 — API 키 불요 구성)

> **결론: 외부 LLM API 키 없이 전체 시스템이 동작한다.** 분석은 ①규칙 엔진 ②로컬 LLM(Ollama) ③Claude Code 헤드리스(구독 인증) 3계층으로 처리한다. Groq는 선택적 폴백으로만 남긴다. 상세는 §11.6.

이 결정의 대가는 **실행 위치**다. Ollama도 Claude Code 구독 인증도 GitHub의 클라우드 러너에서는 쓸 수 없다. 그래서 파이프라인을 두 갈래로 쪼갠다.

| 러너 | 위치 | 실행 계층 | PC 전원 |
|---|---|---|---|
| **클라우드 러너** (GitHub-hosted) | GitHub | **L0 규칙 엔진만** | 무관 — 항상 동작 |
| **셀프호스트 러너** (self-hosted) | 담당자 PC / WSL | **L1 로컬 LLM + L2 Claude Code** | 필요 |

**점진적 향상(Progressive Enhancement) 구조**

```
07:00  클라우드 러너 — L0
       수집 → dedup → 규칙 태깅 → 추출 요약 → articles.json 발행 → 카톡 텍스트 생성
       → 이 시점에 이미 "쓸 수 있는" 아카이브가 완성된다 (analysis_level: "L0")

07:10  셀프호스트 러너 — L1·L2  (PC가 켜져 있을 때만)
       Tier B 생성형 요약·논조 (Ollama)      → analysis_level: "L1"
       Tier A 퓨처엠 시사점 (Claude Code)     → analysis_level: "L2"
       → 기존 articles.json을 덮어쓰지 않고 enrich 후 재발행
```

- PC가 꺼져 있어도 **브리핑은 나간다.** 요약 품질만 추출식으로 낮아진다.
- `articles.json`의 각 기사에 `analysis_level` 필드를 두어 UI에 표시한다 (`⚙️ 규칙요약` / `🤖 AI요약`).
- 이 구조는 오케스트레이터의 재개(resume) 설계와 정확히 맞물린다. L1·L2는 **선택 스테이지**이며 실패해도 L0 산출물이 유효하다.

**셀프호스트 러너 구성**
```bash
# GitHub 저장소 Settings → Actions → Runners → New self-hosted runner
# 워크플로 정의·스케줄·로그는 GitHub에 유지하고 실행만 로컬에서
runs-on: [self-hosted, windows]   # 또는 WSL2 linux
```
> 스케줄·로그·재실행 버튼을 GitHub에 두는 편이 로컬 cron보다 운영이 훨씬 편하다. 로컬 스크립트만 돌리면 실패를 놓친다.

### 6.4 스케줄 (v1.3 재설계 — 07:00 발송 역산)

> **핵심 통찰:** 메일 대상은 **"전날 기사"** 다. 전날 것은 자정이면 이미 확정된다.
> → **07:00에 만들지 말고, 야간에 만들어 두고 07:00에는 발송만 한다.** 이렇게 하면 07:00 데드라인에 쫓기지 않는다.

```
00:20  [클라우드 · L0]  전일 확정분 (전일 00:00~24:00) 수집·정규화·크롤링·규칙태깅·추출요약
       → articles.json 1차 발행 · 메일 초안 생성                    (25분)

00:50  [셀프호스트 · L1·L2]  Tier B 요약(Ollama) → Tier A 시사점(Claude Code)
       → enrich 재발행 · 메일 초안 갱신                              (30~60분)
       ※ PC 야간 가동 필요. Windows 작업 스케줄러의
         "작업 실행을 위해 절전 모드 해제" 옵션으로 자동 기상 가능

06:30  [클라우드 · L0]  당일 새벽 증분 수집 (00:00~06:30) — 카톡·텔레그램 브리핑용

06:40  [체크]  L1·L2 완료 여부 확인 → 미완료 시 셀프호스트 재시도 1회 (§4.11.4)

07:00  [클라우드]  ★발송★
       ├─ 📧 메일 (Part A 전일 포스코 클리핑 + Part B 정책·통상)
       ├─ 📋 카톡 발송 모드 패널 활성화 (담당자가 복사·전송)
       └─ ✈️ 텔레그램 브리핑
```

| 산출물 | 대상 기간 | 근거 |
|---|---|---|
| **메일 Part A·B** | **전일 00:00 ~ 24:00** (`published_at` 기준) | "전날 기사" 요구사항 그대로 |

### 실행 계층 배치 (v1.1)

| 계층 | 에이전트 | 비고 |
|---|---|---|
| **L0 규칙** | A1 collector · A2 normalizer · A3 crawler · **A6 entity-tagger** · **A8 policy-stager** · A12 publisher | LLM 미사용. 사전·정규식·소스타입 기반 |
| **L1 로컬 LLM** | A4 summarizer (Tier B) · A5 tone-judge (Tier B) | Ollama |
| **L2 Claude Code** | A4·A5 (Tier A) · **A7 futurem-analyst** · A9 issue-clusterer · **A10 swot-analyst** · A11 fact-checker | 헤드리스, 구독 인증 |
| **L3 폴백** | A4·A5 (Tier A) | Groq — PC 사용 불가 시에만 |

> **A6 entity-tagger와 A8 policy-stager가 L0로 내려온 것이 v1.1의 큰 변화다.** `posco_relevance`는 카톡 발송 게이트라 **결정론적이어야 안전하다.** LLM 판정은 같은 입력에도 흔들리는데, 발송 여부가 실행할 때마다 달라지면 감사도 재현도 불가능하다. 사전 매칭 + 나열 패턴 예외 규칙이 이 자리에서는 LLM보다 낫다.

| 합치면 안 되는 조합 | 증상 |
|---|---|
| `summarizer` + `tone-judge` | 부정 기사 요약이 부정적 문체로 나와 이후 중립 판정이 불가능 |

## 8. 프롬프트 설계 원칙

### 8.1 공통

- 출력은 **JSON 강제** — 스키마 명시 + "코드펜스·설명 없이 JSON만"
- **요약은 원문 표현 재사용 금지** — 자체 문장 재작성 (저작권 + 검색 품질)
- **근거 없는 서술 금지** — 기사에 없는 배경지식 삽입 금지, 필요 시 `assumptions[]`로 분리
- 판정형 태스크는 **라벨 + 근거 문장 지목**을 함께 요구 → 사후 검증 가능
- 배치 호출 시 **입력 id를 출력에 반드시 echo** → 순서 뒤바뀜 방지 (실제로 자주 발생)
- 실패 시 부분 결과라도 반환하도록 지시, 파서는 부분 파싱 허용

### 8.2 `swot-analyst` 고정 헤더 (그대로 사용)

> 당신은 **포스코퓨처엠** 대외협력 담당자입니다. 아래 기사들이 **포스코퓨처엠에게** 무엇을 의미하는지 분석하십시오.
>
> 규칙:
> 1. **S·W는 반드시 포스코퓨처엠 내부 요인만** 기술하십시오. 경쟁사·정부·시장의 특성은 S·W에 쓸 수 없습니다.
> 2. **O·T는 외부 환경 요인만** 기술하십시오. 경쟁사의 강점은 T입니다.
> 3. 규제·정책은 자동으로 T가 아닙니다. **상대적 유불리**를 따지십시오. 규제 강화가 중국 경쟁사에 더 불리하다면 그것은 포스코퓨처엠에게 O입니다.
> 4. 각 항목에 근거 기사 id를 붙이고, 근거가 없으면 `evidence: []`, `confidence: "low"`로 표기하십시오.
> 5. 추측을 사실처럼 쓰지 마십시오. 모르면 항목을 비우십시오.
> 6. `policy_ask`는 **정부에 실제로 요청 가능한 구체적 조치**여야 합니다. "지원이 필요하다" 같은 문장은 금지입니다.

### 8.3 채널 격리

**메신저 출력 프롬프트에는 `analysis.json` / `issues.json` 컨텍스트를 아예 주입하지 않는다.** 프롬프트로 "말하지 마라"라고 지시하는 것은 방어선이 아니다. 컨텍스트에 없으면 말할 수 없다.

## 9. 제약사항 & 리스크

### 9.1 카카오톡 — 최대 제약 ⚠️

확인된 사실:
- 카카오톡 메시지 API(`friends/message`)는 **친구 개인**에게만 발송 가능, **기존 그룹 채팅방 발송 불가**
- 카카오톡 오픈채팅 API는 **API로 생성·관리한 오픈채팅방**에 한해 메시지 전송 제공 (사용 신청 + 도메인 ID 발급 필요)
- 카카오 공식 오픈채팅봇은 환영/자동응답/알림 수준의 기초 기능만 지원
- 알림 리스너·카톡 DB 접근 방식의 비공식 봇은 **이용약관 위반**으로 계정 정지 가능

→ v1은 Plan D(텔레그램 자동 + 카톡 반자동 복사). Plan B는 팀 합의 시 v2.

### 11.3 스테이지 계약 (Node Contract)

각 스테이지는 아래를 준수한다.

```python
@dataclass
class StageResult:
    stage: str
    status: Literal["success", "partial", "failed", "skipped"]
    input_count: int
    output_count: int
    errors: list[dict]          # {item_id, error_type, message}
    artifacts: list[str]        # 산출 파일 경로
    duration_sec: float
    cost: dict                  # {api_calls, input_tokens, output_tokens, usd}
    checkpoint: str             # 재개 지점 식별자
```

**규칙**
- 스테이지는 **입력 파일 → 출력 파일** 로만 통신한다 (메모리 전달 금지). 재개 가능성의 전제다.
- 출력 파일이 이미 존재하고 `input_hash`가 같으면 **스킵**한다 (멱등성).
- 건별 실패는 `errors[]`에 기록하고 계속 진행. 스테이지 전체 실패는 예외로 중단.

### 11.6 LLM 실행 계층 (v1.1 전면 개정 — API 키 불요)

#### 11.6.1 왜 바꿨는가 — Groq 무료 티어 물량 계산

한국어 기사는 토큰 효율이 낮다(대략 1자 ≈ 1.2토큰). 본문 평균 2,500자 → **약 3,000토큰**.

| 항목 | 계산 | 결과 |
|---|---|---|
| 에이전트 1개 일일 토큰 | 110건 × 3,000 | **330,000** |
| 4개 에이전트 합계 | × 4 | **1,320,000** |

Groq 무료 티어의 일일 토큰 상한(TPD)과 비교하면:

| 모델 | TPD | 초과 배수 |
|---|---|---|
| llama-3.1-8b-instant | ~500,000 | **2.6배 초과** |
| gpt-oss-120b | ~200,000 | **6.6배 초과** |
| llama-3.3-70b-versatile | ~100,000 | **13.2배 초과** |

더 치명적인 건 **분당 토큰(TPM ~6,000)** 이다. 3,000토큰짜리 기사 1건이 분당 예산의 절반을 먹는다.
→ **분당 2건**밖에 처리하지 못한다. 요약만 55분, 4개 에이전트 전부 돌리면 **3.7시간**.

> ⚠️ 즉, **Groq 무료 티어만으로는 현재 설계가 성립하지 않는다.** 배치(5건/호출)도 도움이 안 된다 — TPM 제약 때문에 오히려 한 번에 15,000토큰을 던져 즉시 429가 난다. 무료 티어 수치는 모델별로 자주 바뀌므로 `x-ratelimit-*` 응답 헤더를 런타임 진실원천으로 삼을 것.

#### 11.6.2 해법 ① — LLM에 보낼 물량 자체를 줄인다 (Tier 분류)

| Tier | 대상 | 일일 건수 | 처리 |
|---|---|---|---|
| **A** | **`posco_relevance ≠ none` 전량** OR `sector_impact=direct` 후보 OR `pol-law` 예고 건 OR 티어1 매체 주요기사 | **15~30** | 생성형 요약 + 논조 + **퓨처엠 시사점 + swot_axis** |
| **B** | 카드에 노출되는 나머지 | **40~60** | 생성형 요약 + 논조 |
| **C** | 저중요도 (접힘 노출) | 나머지 | **추출 요약만 (LLM 미사용)** |

→ LLM 투입 물량이 110건 × 4에이전트에서 **Tier A 25건 × 3 + Tier B 50건 × 2 = 175회**로 줄어든다.

> **v2.0 조정:** 요구사항 C3(*"[기사] 당사영향도 분석"*)은 **모든 포스코 기사**에 영향도가 붙어야 한다는 뜻이다. 그래서 `posco_relevance ≠ none` 인 기사는 **impact 등급과 무관하게 전량 Tier A**로 올렸다. 포스코 관련 기사는 하루 10~15건이라 물량 부담이 크지 않다. 반대로 포스코와 무관한 산업 기사까지 영향도를 뽑는 것은 낭비다.

#### 11.6.3 해법 ② — 4계층 실행 구조

| 계층 | 수단 | API 키 | 담당 | 한도 |
|---|---|---|---|---|
| **L0** | **규칙 엔진 (LLM 미사용)** | 불요 | 수집·dedup·prescore·기업/국가/토픽 매칭·`posco_relevance`·`policy_stage`·추출 요약 | 무제한 |
| **L1** | **Ollama 로컬 LLM** | 불요 | Tier B 생성형 요약 + 논조 | 무제한 (PC 성능만) |
| **L2** | **Claude Code 헤드리스** (구독 인증) | 불요 | Tier A 퓨처엠 시사점 · 이슈 클러스터링 · **SWOT** | 구독 사용량 |
| **L3** | Groq 무료 API | 필요 | **선택적 폴백** — PC 사용 불가 시 Tier A만 | TPD/TPM |

**L0 — 규칙 엔진이 생각보다 많은 것을 처리한다**

LLM 없이 정확도가 충분히 나오는 항목들이다. 오히려 LLM보다 안정적이다.

| 항목 | 규칙 |
|---|---|
| `companies` / `countries` | 사전 매칭 (별칭 포함) |
| `posco_relevance` | 계열사명 위치·빈도 + **나열 패턴 예외**(`등`, `3사`, `및` 앞뒤 컨텍스트) |
| `policy_stage` | 소스 타입 + 키워드. Federal Register의 `Proposed Rule`/`Final Rule`, 관보의 `입법예고`·`행정예고`·`공포`·`시행` → **거의 100% 정확** |
| `topics` | 키워드 사전 + 공기어 |
| 추출 요약 | 한국어 뉴스는 역피라미드 구조 → **리드 3문장**이 요약으로 충분히 기능. 네이버 API `description` 병용 |
| `impact` 1차 | `prescore` + 정책 단계 가중 |

> 💡 **핵심 통찰:** 이 시스템에서 LLM이 정말 필요한 부분은 "요약"이 아니라 **"이게 우리에게 무슨 의미인가"(퓨처엠 시사점·SWOT)** 다. 그건 하루 20건, 주간 5~7 이슈다. **소량·고가치**다. 반면 무료 API 한도를 태우는 건 대량·저가치인 요약이다. 이 둘을 같은 자원으로 처리하려 한 것이 v1.0의 설계 오류였다.

**L2 — Claude Code 헤드리스 호출 예시**

```bash
# 구독 인증으로 장기 토큰 발급 (최초 1회, API 키 불요)
claude setup-token

# Tier A 퓨처엠 시사점 — 구조화 출력
claude -p "$(cat prompts/futurem_analyst.md)"   --bare   --output-format json   --json-schema schemas/implication.json   --max-turns 1   --allowedTools "Read"   < work/tier_a_batch.json > work/implications.json

# 주간 SWOT — 이슈 1건당 1회, 주 5~7회
claude -p "@prompts/swot_analyst.md 이슈 파일: work/issue_$ID.json"   --bare --output-format json --json-schema schemas/swot.json
```

- `--bare`는 로컬 `~/.claude` 훅·MCP 설정을 배제해 스크립트 실행을 재현 가능하게 만든다
- `--json-schema`로 파서 실패를 구조적으로 줄인다
- `--max-turns`로 예산 폭주를 막는다
- ⚠️ **구독 사용량 한도가 있다.** L2는 반드시 소량·고가치에만 쓰고, 대량 요약을 L2로 돌리지 않는다

**L1 — Ollama 모델 선정 기준**

| 고려사항 | 내용 |
|---|---|
| 한국어 품질 | 8B급 모델 간 편차가 크다. **실제 기사 20건으로 A/B 비교 후 결정** |
| 하드웨어 | GPU(VRAM 8GB+) → 100건 20~40분 / CPU only → 야간 배치 |
| 후보 | Qwen 계열, Gemma 계열, EEVE 등 한국어 파인튜닝 모델 |
| 검증 | 요약 3줄이 원문 사실과 어긋나지 않는지 20건 수동 확인 |

#### 11.6.4 예산 및 안전장치

| 수단 | 내용 |
|---|---|
| 기본 비용 | **$0** (L0+L1+L2 구성) |
| 본문 절삭 | LLM 입력은 본문 앞 1,200토큰으로 절삭 (역피라미드 구조상 손실 적음) |
| 캐시 | 동일 `content_hash` 재분석 금지 |
| 조건부 실행 | `fact-checker`는 Tier A 중 수치 주장 포함 건만 |
| L3 폴백 상한 | `groq_daily_token_budget` 초과 시 즉시 중단, L0 산출물로 발행 |
| 실패 시 | 어느 계층이 죽어도 **L0 결과로 발행**된다 (INV-6) |

> **INV-6 (신규):** L1·L2·L3는 전부 **선택 스테이지**다. 실패·미실행 시에도 L0 산출물만으로 아카이브·카톡·텔레그램이 정상 동작해야 한다.

### 11.7 실행 모드

```bash
# 일일 실행

# 정책만 경량 폴링
python orchestrator.py --mode policy-watch --tracks policy

# 발송 없이 전 과정 검증
python orchestrator.py --mode daily --dry-run

python orchestrator.py --resume 20260826-0700

# 특정 스테이지만
python orchestrator.py --resume 20260826-0700 --only S4,S6,S7
```

```python
def build_kakao_payload(articles):
    main = [a for a in articles if should_send_kakao(a)]        # 기존 규칙 (INV-4)

    policy_alerts = [
        a for a in articles
        if a.track == "policy"
        and a.sector_impact == "direct"
        and a.impact == "high"
        and a.policy_stage in ("proposed", "enacted", "amended")
        and not should_send_kakao(a)                            # 중복 제외

    policy_alerts.sort(key=lambda a: a.prescore, reverse=True)
    return main, policy_alerts[:1]                              # ★하루 1건 상한★
```

#### P0-6. 사외 → 사내 배포 리스트 수신 허용 확인 *(v1.4 — 사내 확인 결과 문제없음)*

> ✅ **해소.** 사내 배포 리스트 수신에 문제가 없다는 확인을 받았다. §4.11.6 ⑤ 단계적 검증(1주 본인 → 2주 팀원 → 3주 리스트)은 **스팸 학습 방지 목적으로 그대로 권장**하되, 차단 리스크는 낮은 것으로 재평가한다. 아래 원문은 참고용으로 남긴다.


- **해결된 부분:** 발송 한도는 **배포 리스트 주소 1개로 보내면 완전히 해소**된다. 발신자 기준 수신자 1명이므로 개인 Gmail 500통/일, SMTP 100명/메시지 제약에 전혀 걸리지 않는다 (§4.11.6)
- **남은 문제:** 병목이 **수신 측**으로 옮겨갔다. 사내 배포 리스트는 통상 외부 발신자를 차단한다
- **IT에 확인할 것:**
  - [ ] 배포 리스트가 **외부 발신자 메일을 수신**하도록 설정돼 있는가
  - [ ] 아니라면 발신 주소를 **그룹 허용 목록에 등록** 가능한가
  - [ ] 메일 보안 게이트웨이의 **화이트리스트 등록** 절차
  - [ ] **사내 계정 발신**(SMTP 릴레이/Exchange)이 가능한가 ← 가능하면 이게 최선
  - [ ] 외부 계정에서 사내 다수에게 정기 발송하는 것이 정보보호 정책상 허용되는가
- **검증 절차:** 1주차 본인 사내 주소 → 2주차 팀원 2~3명 → 3주차 배포 리스트 (§4.11.6 ⑤). **처음부터 배포 리스트로 쏘면 스팸 신고 한 번에 발신 계정이 통째로 차단될 수 있다**
- **폴백:** 막히면 **텔레그램 `#브리핑` 채널**로 동일 내용 발송. 포맷만 바꾸면 되므로 구현 비용 거의 0

```bash
import yaml, sys

if bad: print("❌ INV-4 위반: filter 없는 라우트", bad); sys.exit(1)
PY

    print("❌ INV-5 위반:", bad); sys.exit(1)
print("✅ INV-5 검사 통과")
PY
```

### 15.2 착수 즉시 확정할 3가지 사전

코드보다 **사전(dictionary)이 먼저**다. 이게 없으면 파이프라인이 무의미한 결과를 낸다.

| 사전 | 내용 | 쓰이는 곳 |
|---|---|---|
| `posco_entities` | 포스코 계열사명·영문·약칭 | `posco_relevance` 판정 = **카톡 발송 게이트** |
| `keywords.yaml` | T1~T4 키워드 매트릭스 | 수집 범위 전체 |
| `affects_futurem` 품목 | 양극재·음극재·전구체·흑연·리튬·니켈 등 | 법령·통상 영향 판정 |

### 15.3 구현 순서 (§10 로드맵 요약)

```
P0 환경·신청 (3일)
  └ 카카오/법령 API 신청 · 셀프호스트 러너 · Ollama · claude setup-token
P1 수집·정규화 (1.5주)   → 4트랙 수집·dedup·상한 동작
P2 크롤링·요약 (1.5주)   → L0 규칙 태깅 + L1 품질 실측(P0-5)
P3 프론트 + 인증 (1.5주) → INV-8 자동 테스트 통과
P4 발송 + 안전장치 (1.5주) → ★섀도 운영 1주 무사고★
P5 정책·통상·법령 탭 (3.5주)
P6 SWOT + 주간 브리프 (2주)
P7 오케스트레이터 (1주)
P8 챗봇 (1주)
```

> **P4를 P5·P6보다 앞에 두는 이유:** 발송은 한 번 잘못 나가면 되돌릴 수 없다. 분석 기능보다 먼저 확정하고 테스트로 고정한다.

### 15.4 불변 규칙 요약 (구현 중 상시 확인)

| INV | 내용 |
|---|---|
| 1 | 요약·크롤링은 전 트랙 공통 |
| 2 | SWOT 기준점은 항상 포스코퓨처엠 |
| 3 | SWOT은 웹에서만 — 발송 경로는 `issues.json`을 import하지 않는다 |
| 4 | 각 발송 대상은 자기 라우트 규칙의 기사만 받는다 |
| 5 | 원문 전문은 클라이언트 접근 경로에 두지 않는다 |
| 6 | L1·L2·L3는 선택 스테이지 — L0만으로도 발행된다 |
| 7 | 메일도 SWOT 차단 대상 |
| 8 | 인증은 서버에서 — `public/`에 데이터를 두지 않고 API가 필드를 걸러 응답 |
| 9 | 메일은 자체 완결적 — 링크 없이도 업무가 된다 |
| 10 | **카카오톡은 §4.7.3 고정 포맷 외로 발송하지 않는다. 깨질 바에는 미발송** |
