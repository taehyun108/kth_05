# 02 — 요약 · 논조 · 영향도 분석

### F-04. 요약 & 분석 (Analyzer)

기사 1건당 아래 필드를 생성한다. **T1·T2·T3 구분 없이 동일 적용** (INV-1).

| 필드 | 생성 에이전트 | 설명 | 공개여부 |
|---|---|---|---|
| `summary` | S4a | 카드용 1~2문장 | 🌐 공개 |
| `bullets[]` | S4a | 핵심 포인트 3~5개 | 🌐 공개 |
| `tone` | S4b | `positive`/`neutral`/`negative`/`crisis` | 🌐 공개 |

| `companies[]` | S4c | 언급 기업 (그룹사+타사) | 🌐 공개 |
| `countries[]` | S4c | 관련 국가 (T3 필수) | 🌐 공개 |
| `topics[]` | S4c | 이슈 태그 | 🌐 공개 |

| `sector_impact` | S4d | `direct`/`indirect`/`none` — 포스코 미언급이어도 산업 영향도 | 🔒 비공개 |
| `futurem_implication` | S4d | 퓨처엠 관점 시사점 1~2문장 | 🔒 비공개 |

> **공개/비공개 구분이 v1.0의 핵심 변경이다.** `futurem_implication`과 `swot_axis`는 사실상 SWOT 분석의 파편이다. 이걸 public `articles.json`에 넣으면 SWOT을 private repo로 옮긴 의미가 없어진다. (§12 검증 3회차)

#### 4.4.1 `posco_relevance` 판정 규칙 (카톡 발송 게이트)

| 값 | 정의 | 판정 방법 | 카톡 |
|---|---|---|---|
| `primary` | 포스코 계열사가 기사의 **주제** | 제목에 계열사명 OR 본문 3회 이상 | ✅ 항상 |
| `mention` | 포스코가 **비교군·인용**으로 언급 | 본문 1~2회, 제목엔 없음 | ✅ `impact ≥ mid` |
| `none` | 미언급 | 계열사명 미등장 | ❌ 웹·텔레그램만 |

**2단계 판정:** ① 문자열 매칭으로 후보 추출 → ② Claude가 맥락 검증
→ *"국내 배터리 3사와 포스코퓨처엠 등"* 같은 단순 나열, 시세표·종목 리스트 언급은 `none`으로 강등한다. 문자열만 쓰면 카톡이 스팸이 된다.

#### 4.4.2 `sector_impact` (v1.0 신규)

정책 트랙 때문에 필요해진 필드다. 예: *"美 45X 음극재 적격비용 축소"* 는 포스코를 한 번도 언급하지 않지만 **직격탄**이다. `posco_relevance=none` 이지만 `sector_impact=direct`.

| 값 | 정의 | 용도 |
|---|---|---|
| `direct` | 퓨처엠 사업에 직접 영향 (제품·원료·고객·규제 대상) | 웹 상단 고정, 텔레그램 긴급, SWOT 우선 |
| `indirect` | 산업 전반 영향, 퓨처엠에 2차 파급 | 일반 노출 |
| `none` | 참고 수준 | 접힘 노출 |

> ⚠️ **`sector_impact`는 카톡 게이트에 사용하지 않는다.** 사용자 요구사항(INV-4)은 "포스코가 언급되어 있으면 카톡 송부"이므로 게이트는 `posco_relevance` 단독이다. 다만 이 때문에 *"우리에게 가장 중요한 정책 기사가 카톡에 안 뜨는"* 상황이 발생한다 → **§13-P0-2 결정 필요**.

#### 4.4.3 논조 판정 기준

- `crisis`: 안전사고·법적분쟁·규제제재·오너리스크 등 즉시 대응 필요
- `negative`: 실적·경쟁력·평판에 부정적 서술이 주된 논지
- `neutral`: 사실 전달, 단순 실적/공시/인사/정책 발표
- `positive`: 수주·기술성과·정책수혜

> **T2·T3 기사의 논조는 "기사 자체의 논조"를 판정한다.** 경쟁사 호재는 기사 논조 `positive`이고, 우리 입장의 위협은 `swot_axis=T`로 표현한다. 두 개념을 섞으면 경쟁사 호재 기사가 전부 `negative`로 라벨링돼 통계가 무의미해진다.

#### 4.4.4 중요도(impact) 판정

```
high =
    tone == crisis
 OR (posco_relevance == primary AND tone == negative AND outlet_tier <= 2)
 OR (track == battery AND 밸류체인 구조 변화급: 대형 증설·기술 상용화·대형 수주)
 OR (track == policy AND sector_impact == direct AND 확정/시행/개정 단계)
```

**정책 단계 가중 (T3 전용)** — 같은 주제라도 단계에 따라 중요도가 다르다.

| 단계 | 코드 | 가중 |
|---|---|---|
| 논의·검토 | `discussion` | 낮음 |
| 입법예고·공고 | `proposed` | **높음 (선제 대응 기회)** |
| 확정·공포 | `enacted` | 높음 |
| 시행 | `effective` | 중간 |
| 개정·폐지 | `amended` | 높음 |

### 11.6 LLM 실행 계층 (v1.1 전면 개정 — API 키 불요)

#### 11.6.1 왜 바꿨는가 — Groq 무료 티어 물량 계산

한국어 기사는 토큰 효율이 낮다(대략 1자 ≈ 1.2토큰). 본문 평균 2,500자 → **약 3,000토큰**.

| 항목 | 계산 | 결과 |
|---|---|---|
| 에이전트 1개 일일 토큰 | 110건 × 3,000 | **330,000** |
| 4개 에이전트 합계 | × 4 | **1,320,000** |

Groq 무료 티어의 일일 토큰 상한(TPD)과 비교하면:

| 모델 | TPD | 초과 배수 |
|---|---|---|
| llama-3.1-8b-instant | ~500,000 | **2.6배 초과** |
| gpt-oss-120b | ~200,000 | **6.6배 초과** |
| llama-3.3-70b-versatile | ~100,000 | **13.2배 초과** |

더 치명적인 건 **분당 토큰(TPM ~6,000)** 이다. 3,000토큰짜리 기사 1건이 분당 예산의 절반을 먹는다.
→ **분당 2건**밖에 처리하지 못한다. 요약만 55분, 4개 에이전트 전부 돌리면 **3.7시간**.

> ⚠️ 즉, **Groq 무료 티어만으로는 현재 설계가 성립하지 않는다.** 배치(5건/호출)도 도움이 안 된다 — TPM 제약 때문에 오히려 한 번에 15,000토큰을 던져 즉시 429가 난다. 무료 티어 수치는 모델별로 자주 바뀌므로 `x-ratelimit-*` 응답 헤더를 런타임 진실원천으로 삼을 것.

#### 11.6.2 해법 ① — LLM에 보낼 물량 자체를 줄인다 (Tier 분류)

| Tier | 대상 | 일일 건수 | 처리 |
|---|---|---|---|
| **A** | **`posco_relevance ≠ none` 전량** OR `sector_impact=direct` 후보 OR `pol-law` 예고 건 OR 티어1 매체 주요기사 | **15~30** | 생성형 요약 + 논조 + **퓨처엠 시사점 + swot_axis** |
| **B** | 카드에 노출되는 나머지 | **40~60** | 생성형 요약 + 논조 |
| **C** | 저중요도 (접힘 노출) | 나머지 | **추출 요약만 (LLM 미사용)** |

→ LLM 투입 물량이 110건 × 4에이전트에서 **Tier A 25건 × 3 + Tier B 50건 × 2 = 175회**로 줄어든다.

> **v2.0 조정:** 요구사항 C3(*"[기사] 당사영향도 분석"*)은 **모든 포스코 기사**에 영향도가 붙어야 한다는 뜻이다. 그래서 `posco_relevance ≠ none` 인 기사는 **impact 등급과 무관하게 전량 Tier A**로 올렸다. 포스코 관련 기사는 하루 10~15건이라 물량 부담이 크지 않다. 반대로 포스코와 무관한 산업 기사까지 영향도를 뽑는 것은 낭비다.

#### 11.6.3 해법 ② — 4계층 실행 구조

| 계층 | 수단 | API 키 | 담당 | 한도 |
|---|---|---|---|---|
| **L0** | **규칙 엔진 (LLM 미사용)** | 불요 | 수집·dedup·prescore·기업/국가/토픽 매칭·`posco_relevance`·`policy_stage`·추출 요약 | 무제한 |
| **L1** | **Ollama 로컬 LLM** | 불요 | Tier B 생성형 요약 + 논조 | 무제한 (PC 성능만) |
| **L2** | **Claude Code 헤드리스** (구독 인증) | 불요 | Tier A 퓨처엠 시사점 · 이슈 클러스터링 · **SWOT** | 구독 사용량 |
| **L3** | Groq 무료 API | 필요 | **선택적 폴백** — PC 사용 불가 시 Tier A만 | TPD/TPM |

**L0 — 규칙 엔진이 생각보다 많은 것을 처리한다**

LLM 없이 정확도가 충분히 나오는 항목들이다. 오히려 LLM보다 안정적이다.

| 항목 | 규칙 |
|---|---|
| `companies` / `countries` | 사전 매칭 (별칭 포함) |
| `posco_relevance` | 계열사명 위치·빈도 + **나열 패턴 예외**(`등`, `3사`, `및` 앞뒤 컨텍스트) |
| `policy_stage` | 소스 타입 + 키워드. Federal Register의 `Proposed Rule`/`Final Rule`, 관보의 `입법예고`·`행정예고`·`공포`·`시행` → **거의 100% 정확** |
| `topics` | 키워드 사전 + 공기어 |
| 추출 요약 | 한국어 뉴스는 역피라미드 구조 → **리드 3문장**이 요약으로 충분히 기능. 네이버 API `description` 병용 |
| `impact` 1차 | `prescore` + 정책 단계 가중 |

> 💡 **핵심 통찰:** 이 시스템에서 LLM이 정말 필요한 부분은 "요약"이 아니라 **"이게 우리에게 무슨 의미인가"(퓨처엠 시사점·SWOT)** 다. 그건 하루 20건, 주간 5~7 이슈다. **소량·고가치**다. 반면 무료 API 한도를 태우는 건 대량·저가치인 요약이다. 이 둘을 같은 자원으로 처리하려 한 것이 v1.0의 설계 오류였다.

**L2 — Claude Code 헤드리스 호출 예시**

```bash
# 구독 인증으로 장기 토큰 발급 (최초 1회, API 키 불요)
claude setup-token

# Tier A 퓨처엠 시사점 — 구조화 출력
claude -p "$(cat prompts/futurem_analyst.md)"   --bare   --output-format json   --json-schema schemas/implication.json   --max-turns 1   --allowedTools "Read"   < work/tier_a_batch.json > work/implications.json

# 주간 SWOT — 이슈 1건당 1회, 주 5~7회
claude -p "@prompts/swot_analyst.md 이슈 파일: work/issue_$ID.json"   --bare --output-format json --json-schema schemas/swot.json
```

- `--bare`는 로컬 `~/.claude` 훅·MCP 설정을 배제해 스크립트 실행을 재현 가능하게 만든다
- `--json-schema`로 파서 실패를 구조적으로 줄인다
- `--max-turns`로 예산 폭주를 막는다
- ⚠️ **구독 사용량 한도가 있다.** L2는 반드시 소량·고가치에만 쓰고, 대량 요약을 L2로 돌리지 않는다

**L1 — Ollama 모델 선정 기준**

| 고려사항 | 내용 |
|---|---|
| 한국어 품질 | 8B급 모델 간 편차가 크다. **실제 기사 20건으로 A/B 비교 후 결정** |
| 하드웨어 | GPU(VRAM 8GB+) → 100건 20~40분 / CPU only → 야간 배치 |
| 후보 | Qwen 계열, Gemma 계열, EEVE 등 한국어 파인튜닝 모델 |
| 검증 | 요약 3줄이 원문 사실과 어긋나지 않는지 20건 수동 확인 |

#### 11.6.4 예산 및 안전장치

| 수단 | 내용 |
|---|---|
| 기본 비용 | **$0** (L0+L1+L2 구성) |
| 본문 절삭 | LLM 입력은 본문 앞 1,200토큰으로 절삭 (역피라미드 구조상 손실 적음) |
| 캐시 | 동일 `content_hash` 재분석 금지 |
| 조건부 실행 | `fact-checker`는 Tier A 중 수치 주장 포함 건만 |
| L3 폴백 상한 | `groq_daily_token_budget` 초과 시 즉시 중단, L0 산출물로 발행 |
| 실패 시 | 어느 계층이 죽어도 **L0 결과로 발행**된다 (INV-6) |

> **INV-6 (신규):** L1·L2·L3는 전부 **선택 스테이지**다. 실패·미실행 시에도 L0 산출물만으로 아카이브·카톡·텔레그램이 정상 동작해야 한다.
